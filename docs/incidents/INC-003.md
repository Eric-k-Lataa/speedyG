## Identificación

* **Caso de prueba relacionado:** TC-005 (Cancelación de trabajos y manejo de procesos en el SO)
* **Severidad:** Crítica
* **Fecha de detección:** 2026-11-02

## Síntomas

Al solicitar la cancelación de un trabajo en estado `Running` mediante el comando `speedyg cancel <id>`, el cliente CLI y el daemon respondían exitosamente indicando que el trabajo había sido cancelado, y las consultas posteriores (`speedyg status <id>`) reportaban el estado `[Canceled]`.

Sin embargo, al inspeccionar la tabla de procesos del sistema operativo (`ps aux | grep sleep`), el subproceso asociado al comando (por ejemplo, `sleep 1001`) **continuaba en ejecución activa**, consumiendo tiempo de CPU y memoria, y quedando completamente desvinculado del control de speedyG.

Esto generaba una violación grave de los requisitos del sistema:
1. **RNF-27 (Consistencia):** Estado imposible donde la máquina de estados afirma que el trabajo está `Canceled`, pero su proceso físico sigue ejecutándose.
2. **RNF-30 (Procesos huérfanos):** El daemon dejaba procesos huérfanos bajo el init del sistema tras una cancelación.

---

## Evidencia (recopilada antes de la corrección)

### 1. Interacción con el cliente CLI y respuesta del daemon:
```bash
$ speedyg sleep 1001
Job #1 encolado correctamente

$ speedyg status 1
Job #1: sleep 1001 [Running]

$ speedyg cancel 1
Job #1 cancelado correctamente

$ speedyg status 1
Job #1: sleep 1001 [Canceled]
```

### 2. Inspección del sistema operativo tras la supuesta cancelación:
```bash
$ ps -eo pid,ppid,pgid,comm,args | grep "sleep 1001"
 14820     1 14819 sleep           sleep 1001
```

* **Observación crítica:** El proceso `sleep 1001` (PID 14820) continuó vivo. Su proceso padre original (el shell `sh` lanzado por speedyG) murió, y el proceso hijo fue adoptado por el proceso `init` (`PPID=1`), quedando como proceso huérfano e incontrolable.

---

## Hipótesis contrastadas

### Hipótesis 1 (Falta de emisión de señales en el Scheduler):
* **Planteamiento:** La función `cancel_job` del scheduler únicamente realizaba una mutación lógica en memoria (`job.state = JobState::Canceled`), pero no invocaba ninguna función para enviar señales de terminación (`SIGTERM`/`SIGKILL`) al PID del proceso hijo en el sistema operativo.
* **Resultado del contraste (Confirmada parcialmente):** Al revisar el código de `src/scheduler.rs`, se constató que efectivamente solo se cambiaba el enum de estado y no existía llamada al sistema para matar el subproceso.

### Hipótesis 2 (Señal insuficiente ante subárboles de procesos / Shell wrapper):
* **Planteamiento:** Al invocar comandos a través de `sh -c "<comando>"`, el proceso directo creado por Rust es `/bin/sh`. Si el daemon únicamente envía `kill` al PID de `sh`, el shell muere de inmediato pero el comando descendiente (`sleep 1001`) sobrevive como proceso huérfano al no formar parte de un grupo de procesos aislado.
* **Resultado del contraste (Confirmada):** Al probar una solución ingenua que solo ejecutaba `child.kill()` sobre el proceso de Rust, el subproceso `sleep` continuaba vivo en el sistema operativo con `PPID=1`. Se requería necesariamente manejar grupos de procesos (`PGID`) y señales a nivel de grupo (`killpg`).

---

## Causa raíz

La causa raíz estuvo compuesta por dos factores:
1. **Ausencia de propagación de señales:** El scheduler no tenía integrado un mecanismo para interactuar con el sistema operativo al momento de ejecutar cancelaciones sobre trabajos en ejecución.
2. **Falta de aislamiento de grupos de procesos:** Los comandos lanzados mediante `Command::new("sh").arg("-c")` creaban un árbol de procesos donde la terminación del padre no garantizaba la muerte de los hijos sin la asignación explícita de un Process Group ID (`process_group(0)`) y la emisión de señales con `killpg`.

---

## Corrección implementada

En el commit **`a1109ab`** (Issue `#62`), se aplicó la solución integral:

1. **Creación de grupos de procesos en [`src/executor.rs`](src/executor.rs):**
   ```rust
   #[cfg(unix)]
   {
       command.process_group(0);
   }
   ```
2. **Manejo de señales POSIX con `nix` en [`src/executor.rs`](src/executor.rs):**
   Implementación de terminación forzada y recolección síncrona enviando `SIGKILL`/`SIGTERM` a todo el grupo de procesos (`PGID`), garantizando que tanto el shell como todos sus subprocesos hijos sean eliminados atómicamente.
3. **Registro inmediato de PID en [`src/main.rs`](src/main.rs):**
   El PID se registra en el scheduler de forma inmediata tras el `spawn`, asegurando que cualquier cancelación concurrente posterior conozca el PID/PGID exacto a terminar.

## Regresión automatizada

Para garantizar que este defecto no vuelva a introducirse en el proyecto, se implementó el caso de prueba automatizado **`TC-005`** en [`verif/scripts/TC-005.sh`](verif/scripts/TC-005.sh), el cual forma parte de la suite general [`verif/scripts/run-all.sh`](verif/scripts/run-all.sh).

### Verificaciones automatizadas en TC-005:
1. Envío de trabajo `A` (`sleep 1001`) y verificación de paso a `Running`.
2. Emisión de `speedyg cancel <id_A>`.
3. Verificación de que `status` reporta `[Canceled]`.
4. **Comprobación estricta en el SO:**
   ```bash
   REMAINING=$(pgrep -f "sleep 1001" 2>/dev/null | grep -c .) || REMAINING=0
   check "El proceso de A ('sleep 1001') deja de existir en el SO dentro de 2s" \
       "$([[ "$REMAINING" -eq 0 ]] && echo 0 || echo 1)"
   ```
5. Validación de ausencia de procesos zombis mediante `check_no_zombies`.
