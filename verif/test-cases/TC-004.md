# TC-004 — Consultar y listar trabajos

> **PROVISIONAL.** La sintaxis del filtro por estado (RF-09) y el contenido de `status <id>` no están definidos en los requisitos ni en los ADR. Este caso fija un contrato mínimo (sección 6). Cuando se implemente A2-07 hay que confirmarlo o ajustarlo; en el script basta cambiar `FILTER_FMT`.

## 2. Objetivo

Verificar que el usuario puede consultar un trabajo por su ID (RF-08), listar los trabajos con un filtro básico por estado (RF-09) y que la consulta responde en **1 s o menos** con **100 trabajos almacenados** (RNF-05).

> Los resultados esperados se derivan de los requisitos y de este contrato, no del comportamiento observado del código.

## 3. Precondiciones

1. El proyecto debe compilar (`cargo build`). El script usa `target/debug/`.
2. El script debe tener permisos de ejecución (`verif/scripts/TC-004.sh`).
3. Socket Unix y directorio de datos temporales y propios de la corrida; persistencia aislada con `SPEEDYG_DB` y `SPEEDYG_JSON`.
4. El daemon se inicia con parámetros explícitos:

```bash
speedyG --socket <socket-temporal> --data-dir <datos-temporales> --max-current 1 --queue-cap 100
```

5. El script comprueba en `daemon.log` que `max_current=1` y `queue_cap=100`; si no, el caso queda **BLOCKED**.
6. La **parte C (filtro)** requiere que el daemon soporte el filtro (A2-07). Si no lo soporta, esa parte queda **BLOCKED**, no FAIL.

> `queue_cap=100` evita rechazos al cargar 100 trabajos. `max_current=1` permite tener a la vez trabajos en `Queued` y `Running`.

## 4. Datos de prueba

### 4.1 Trabajos de preparación (un trabajo por estado)

| Clave | Comando | Estado objetivo |
| --- | --- | --- |
| S | `echo hola` | `Succeeded`, exit code 0 |
| F | `false` | `Failed`, exit code 1 |
| R | `sleep 8` | `Running` durante las consultas |
| Q1 | `echo en-cola-1` | `Queued` |
| Q2 | `echo en-cola-2` | `Queued` |
| X | `echo cancelar` | `Canceled` (se cancela en cola) |

Se envían S y F, se espera a que terminen; luego R, Q1, Q2 y X, y se cancela X.

### 4.2 Carga para RNF-05

100 trabajos `echo carga-N` (N = 1…100). Se espera a que todos terminen, de modo que el sistema almacene más de 100 registros (6 de preparación + 100 de carga).

### 4.3 Parámetros de medición

| Parámetro | Valor |
| --- | --- |
| Repeticiones por tipo de consulta | 10 |
| Criterio | El **máximo** de las 10 mediciones ≤ 1,0 s |
| Reloj | `date +%s.%N` antes y después de ejecutar el cliente (incluye arranque del cliente y conexión) |
| Timeout por consulta | 10 s |

Se evalúa el máximo y no el promedio para que un solo valor lento no quede oculto.

## 5. Procedimiento

1. Ejecutar `cargo build` y `./verif/scripts/TC-004.sh`.
2. El script crea el entorno, arranca el daemon y valida la configuración.
3. Prepara un trabajo en cada estado (sección 4.1) y toma una instantánea con `status` y con `list`.
4. **Parte A (RF-08):** consulta por ID cada uno de los 6 trabajos, un ID inexistente y un ID no numérico.
5. **Parte B (RF-09):** compara el listado completo con los trabajos enviados.
6. **Parte C (RF-09):** envía una sonda de filtro. Si el daemon no la soporta, registra BLOCKED; si la soporta, filtra por cada estado y por un estado inexistente.
7. **Parte D (RNF-05):** espera a que terminen R, Q1 y Q2, envía los 100 trabajos de carga, espera a que terminen y mide 10 veces `status <id>`, `status` (listado completo) y, si hay filtro, la consulta filtrada.
8. Comprueba que no quedan procesos hijos del daemon y detiene el daemon.

## 6. Resultados esperados

### RF-08 — Consulta por ID

- `status <id>` responde con una línea que empieza con `Job #<id>:`.
- La línea incluye el comando enviado y el estado actual entre corchetes.
- Estados esperados: S `Succeeded`, F `Failed`, R `Running`, Q1 y Q2 `Queued`, X `Canceled`.
- S muestra `exit code: 0` y F muestra `exit code: 1`.
- Un ID inexistente responde de forma explícita que no se encontró e incluye el ID consultado.
- Un ID no numérico se rechaza con un mensaje; no se interpreta como una consulta válida.

### RF-09 — Listado

- `status` sin argumentos lista exactamente los 6 trabajos, sin repetir ninguno.
- El estado de cada trabajo en el listado coincide con el de la consulta por ID.
- `list` devuelve los mismos trabajos que `status`.

### RF-09 — Filtro por estado (contrato provisional)

```text
speedyg status --state <Estado>
```

| Elemento | Contrato |
| --- | --- |
| Sintaxis | `status --state <Estado>` |
| Estados válidos | `Queued`, `Running`, `Succeeded`, `Failed`, `Canceled` |
| Salida | Una línea `Job #N: ...` por cada trabajo del estado pedido, y ninguno de otro estado |
| Estado sin trabajos | Salida vacía o un mensaje de que no hay trabajos; nunca el listado completo |
| Estado inexistente | Mensaje de error; nunca el listado completo |

### RNF-05 — Tiempo de respuesta

Con al menos 100 trabajos almacenados y ninguno pendiente:

- `status <id>`: máximo de 10 mediciones ≤ 1,0 s.
- `status` (listado completo): máximo ≤ 1,0 s, y devuelve todos los trabajos.
- Consulta filtrada (si está soportada): máximo ≤ 1,0 s.

## 8. Criterios PASS/FAIL/BLOCKED

### PASS

1. El daemon cargó `max_current=1` y `queue_cap=100`.
2. Se cumplen todos los criterios de las partes A, B, C y D de la sección 6.
3. Los 100 trabajos de carga son aceptados y terminan.
4. Todas las mediciones máximas ≤ 1,0 s.
5. Al terminar no quedan procesos hijos ni zombis del daemon.

### FAIL

1. El estado, comando o código de salida de una consulta no coincide con lo esperado.
2. El listado omite, repite o inventa un trabajo.
3. El filtro (cuando existe) devuelve un trabajo de otro estado, omite uno del estado pedido o devuelve el listado completo ante un estado inexistente.
4. Un ID inexistente o no numérico se acepta como válido o no incluye mensaje.
5. Alguna medición máxima supera 1,0 s.
6. Los trabajos de carga son rechazados o se pierden.
7. Quedan procesos hijos o zombis del daemon.

### BLOCKED

- El daemon no cargó la configuración esperada o no pudo iniciarse.
- **Parte C y consulta filtrada de la parte D:** el daemon no soporta el filtro por estado (A2-07). Las demás partes se evalúan; el resultado global es `BLOCKED` si no hay FAIL, y el script termina con código 3.

RF-08 y RNF-05 pueden pasar a PASS sin el filtro. RF-09 solo pasa a PASS cuando el filtro se evalúa y cumple.
