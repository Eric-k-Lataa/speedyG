## 2. Objetivo

Verificar que el protocolo de red del servicio:

- **RF-21.** Delimita mensajes, identifica errores y tolera lecturas o escrituras parciales.
- **RF-22.** Maneja desconexiones del cliente sin terminar el servicio ni corromper trabajos.
- **RNF-14.** Valida longitudes y formato de los mensajes de red.
- **RNF-24.** Funciona con mensajes fragmentados y múltiples solicitudes secuenciales.

> Los resultados esperados se derivan exclusivamente de estos requisitos. `docs/protocol.md` aún no existe: el delimitador de mensajes se configura con `TC012_DELIM` y debe confirmarse al publicarse el protocolo.

## 3. Precondiciones

1. El proyecto debe compilar (`cargo build`). El script usa `target/debug/speedyG` y `target/debug/speedyg`.
2. `python3` disponible (el script envía bytes fragmentados con `verif/scripts/lib/net_probe.py`).
3. El script de verificación debe tener permisos de ejecución (`verif/scripts/TC-012.sh`).
4. Socket Unix y directorio de datos temporales aislados por corrida (`setup_run_env`).
5. Los PR de A3-04 (framing) y A3-05 (validación) integrados. Si no lo están, usar `TC012_PENDING_PRS=1` (ver sección 8, BLOCKED).

## 4. Datos de prueba

| Dato | Valor |
| ---- | ----- |
| Mensaje válido corto | `health` |
| Mensaje válido con argumento | `echo fragmentado` |
| Mensaje sobredimensionado | `echo ` + 1 048 576 bytes `a` |
| UTF-8 inválido | `echo ` + bytes `0xFF 0xFE 0xFD` |
| Mensaje vacío | 0 bytes |
| Particiones aleatorias | Fragmentos de 1 a 5 bytes, semillas 1, 2 y 3 |
| Delimitador | `TC012_DELIM` (por defecto, salto de línea) |

## 5. Procedimiento

```bash
cargo build
bash verif/scripts/TC-012.sh
```

| Bloque | Qué se hace | Requisitos |
| ------ | ----------- | ---------- |
| **A** | Enviar `health` completo, byte a byte y en particiones aleatorias; enviar `echo fragmentado` byte a byte. | RF-21, RNF-24 |
| **B** | Enviar 3 solicitudes `health` en una misma conexión, de golpe y byte a byte. | RF-21, RNF-24 |
| **C** | Enviar un mensaje sobredimensionado, uno con UTF-8 inválido y uno vacío; tras cada uno enviar una solicitud válida. | RNF-14, RF-21 |
| **D** | Con un trabajo `sleep 30` ya aceptado, cerrar clientes antes de enviar, a medio mensaje y esperando respuesta; consultar el trabajo y enviar uno nuevo. | RF-22 |

## 6. Resultados esperados

### RF-21 y RNF-24 — Fragmentación y solicitudes secuenciales

- El mensaje fragmentado (byte a byte o en particiones aleatorias) produce la misma respuesta que el mismo mensaje enviado completo.
- Un mensaje con argumentos enviado fragmentado se interpreta como **un único** trabajo.
- Tres solicitudes enviadas en una conexión reciben tres respuestas, una por solicitud, tanto de golpe como byte a byte.

### RNF-14 — Validación de longitud y formato

- El mensaje sobredimensionado, el de UTF-8 inválido y el vacío se identifican como error en la respuesta.
- Tras cada mensaje inválido el protocolo se recupera: la siguiente solicitud válida responde correctamente.

### RF-22 — Desconexión del cliente

- El servicio sigue activo y responde tras un cliente que se desconecta antes de enviar, a medio mensaje o esperando respuesta.
- El trabajo aceptado antes de las desconexiones sigue consultable en un estado válido.
- Se acepta un trabajo nuevo tras las desconexiones.

## 8. Criterios PASS/FAIL/BLOCKED

### PASS

Se cumplen **todos** los criterios de la sección 6, el script termina con código 0 y el `run-id` queda citado.

### FAIL

1. Cualquier comprobación de la sección 6 no se cumple.
2. El servicio termina o deja de responder tras un mensaje inválido o una desconexión.

### BLOCKED

- `python3` no está disponible.
- Los PR de A3-04 (framing) y A3-05 (validación) no están integrados: con `TC012_PENDING_PRS=1`, las comprobaciones de solicitudes secuenciales (B1, B2) y de rechazo de mensajes inválidos (C1 a C3) se registran como `BLOCKED` en lugar de `FAIL`. Las demás siguen evaluándose.
