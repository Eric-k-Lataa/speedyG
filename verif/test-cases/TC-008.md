# TC-008 — Aislamiento de fallo: matar un hijo no afecta a los demás Running ni al daemon

## 1. Identificación

| Campo | Valor |
| ------- | ------- |
| **ID** | TC-008 |
| **Título** | Aislamiento de fallo: matar un hijo no afecta a los demás Running ni al daemon |
| **Prioridad** | Crítica |
| **Método** | Prueba |
| **Tipo** | Robustez / Integración / Aislamiento |
| **Requisitos** | RNF-08, RNF-09 |
| **Estado** | Pendiente |

## 2. Objetivo

Verificar que el sistema garantiza el aislamiento de fallos entre procesos independientes y la continuidad operativa del servicio daemon, conforme a los requisitos no funcionales RNF-08 y RNF-09:

1. **RNF-09 (Aislamiento de fallos entre trabajos):** La terminación anormal o forzada de un trabajo (por ejemplo, al recibir una señal `SIGKILL` / `kill -9` externa directamente en el sistema operativo) **no debe afectar a los demás trabajos** que se encuentran ejecutándose concurrentemente (`Running`), los cuales continúan su ejecución con normalidad, ni debe afectar la estabilidad del daemon.
2. **RNF-08 (Resiliencia del servicio ante fallos e incorrecciones):** Una solicitud inválida o una terminación anormal en un subproceso hijo no debe terminar el servicio. El daemon debe permanecer en ejecución y continuar respondiendo solicitudes legítimas de consulta y control (`health`, `status`, nuevos envíos).

> Los resultados esperados se derivan de **RNF-08** y **RNF-09**, asegurando que cada trabajo se ejecuta de forma aislada y que el daemon es resiliente ante fallos imprevistos en los procesos subordinados.

## 3. Precondiciones

1. El proyecto debe compilar correctamente (`cargo build`). El script usa el binario generado en `target/debug/speedyG`.
2. El script de verificación debe tener permisos de ejecución (`verif/scripts/TC-008.sh`).
3. Socket Unix y directorio de datos temporales aislados por corrida (`setup_run_env`), con persistencia explícita en `SPEEDYG_DB` o `SPEEDYG_JSON`.
4. El daemon se inicia con capacidad de concurrencia suficiente para ejecutar múltiples trabajos en paralelo:

```bash
speedyG --socket <socket-temporal> --data-dir <datos-temporales> --max-current 3 --queue-cap 10
```

5. El script verifica en `daemon.log` que la configuración efectiva coincide con la solicitada (`max_current=3`, `queue_cap=10`); en caso contrario, el caso queda **BLOCKED**.
6. Se dispone de utilidades del sistema (`pgrep`, `kill`, `ps`) para inspeccionar procesos y enviar señales específicas a subprocesos hijos.

## 4. Datos de prueba

Se definen tres trabajos de ejecución sostenida con argumentos únicos para rastrear individualmente sus procesos en el sistema operativo, junto con una solicitud intencionalmente inválida:

| Identificador | Comando | Estado esperado inicial | Papel en la prueba | Requisito evaluado |
| --- | --- | --- | --- | --- |
| **J1** | `sleep 1001` | `Running` | **Trabajo testigo A:** Permanece en ejecución antes, durante y después del kill de J2 | RNF-09 |
| **J2** | `sleep 1002` | `Running` | **Trabajo víctima:** Subproceso al que se le inyectará `SIGKILL` (`kill -9`) de forma externa | RNF-09 |
| **J3** | `sleep 1003` | `Running` | **Trabajo testigo B:** Segundo trabajo concurrente que debe continuar intacto | RNF-09 |
| **Solicitud inválida** | Comando no reconocido / sintaxis inválida | N/A | **Prueba de resiliencia:** Envío de comando malformado para verificar que el servicio no cae | RNF-08 |

### 4.1 Parámetros temporales

| Parámetro | Valor |
| --- | --- |
| Concurrencia máxima (`max_current`) | `3` |
| Tiempo de estabilización de J1, J2 y J3 en `Running` | 2 s |
| Señal enviada a J2 | `SIGKILL` (`kill -9 <PID_J2>`) |
| Tiempo de observación posterior al kill de J2 | 3 s |
| Timeout total del caso | 45 s |

## 5. Procedimiento

1. Compilar el proyecto con `cargo build`.
2. Ejecutar `./verif/scripts/TC-008.sh`.
3. Iniciar el daemon en un entorno temporal aislado con `--max-current 3 --queue-cap 10`.
4. Registrar el PID del daemon y validar que se cargó la configuración esperada (`daemon-pid.txt`).
5. **Fase 1 — Lanzamiento de trabajos concurrentes:**
   - Enviar simultáneamente J1 (`sleep 1001`), J2 (`sleep 1002`) y J3 (`sleep 1003`).
   - Esperar 2 s a que los tres trabajos pasen a estado `Running`.
   - Consultar `status` y verificar que los tres trabajos están en `Running` (`status-pre-kill.txt`).
6. **Fase 2 — Identificación de PIDs en el sistema operativo:**
   - Localizar y registrar el PID del proceso de J1 (`pgrep -f "sleep 1001"`).
   - Localizar y registrar el PID del proceso de J2 (`pgrep -f "sleep 1002"`).
   - Localizar y registrar el PID del proceso de J3 (`pgrep -f "sleep 1003"`).
   - Guardar los PIDs iniciales en `pids-pre-kill.txt`.
7. **Fase 3 — Inyección de terminación anormal a J2 (kill -9):**
   - Enviar señal `kill -9` directamente al PID del subproceso de J2 (`sleep 1002`).
   - Registrar la ejecución de la señal en `kill-victim.log`.
8. **Fase 4 — Verificación de aislamiento de fallo (RNF-09):**
   - Esperar 2 s tras el kill de J2.
   - Verificar en el sistema operativo que el proceso de J1 **sigue vivo** (`kill -0 <PID_J1>`).
   - Verificar en el sistema operativo que el proceso de J3 **sigue vivo** (`kill -0 <PID_J3>`).
   - Consultar `status` en el daemon y verificar que J1 y J3 **continúan en estado `Running`** (`status-post-kill.txt`).
   - Verificar que el proceso del daemon **sigue vivo con el mismo PID original** (`kill -0 <DAEMON_PID>`).
9. **Fase 5 — Verificación de resiliencia del servicio ante solicitudes inválidas (RNF-08):**
   - Enviar una solicitud inválida o malformada al daemon (`comando_invalido_xyz_999`).
   - Verificar que el daemon rechaza la solicitud informando el error y continúa operando.
   - Enviar comando `health` y verificar respuesta afirmativa `OK` (`health-check.txt`).
10. **Fase 6 — Limpieza y comprobación de procesos:**
    - Cancelar o esperar la terminación de J1 y J3.
    - Verificar que no existen procesos zombis bajo el PID del daemon (`check_no_zombies`).
    - Detener el daemon y concluir el caso.

## 6. Resultados esperados

### RNF-09 — Aislamiento de la terminación anormal de un trabajo

- La terminación forzada de J2 mediante `kill -9` no provoca la terminación ni interrupción de J1 ni de J3.
- Los subprocesos en el SO correspondientes a `sleep 1001` y `sleep 1003` continúan existiendo ininterrumpidamente con sus PIDs originales.
- Las consultas de `status` para J1 y J3 reportan consistentemente el estado `Running` tras la muerte de J2.
- El PID del daemon se mantiene idéntico al registrado al inicio (el daemon no sufrió *panic*, reinicio ni caída).

### RNF-08 — Continuidad del servicio ante fallos y solicitudes inválidas

- El daemon permanece en ejecución tras la muerte abrupta del subproceso hijo J2.
- El daemon permanece en ejecución tras recibir solicitudes inválidas o sintácticamente incorrectas.
- El daemon responde exitosamente a consultas de control (`health` devuelve `OK`).

### Ausencia de procesos zombi o residuales

- El subproceso de J2 es cosechado adecuadamente sin quedar como proceso zombi permanente.
- Al finalizar la prueba no quedan procesos huérfanos asociados a los marcadores de la prueba.

## 8. Criterios PASS/FAIL/BLOCKED

### PASS

Se cumplen **todos** los siguientes criterios:

1. El daemon inicia correctamente y carga la configuración requerida (`max_current=3`, `queue_cap=10`).
2. J1, J2 y J3 entran simultáneamente en estado `Running`.
3. Al terminar forzadamente el subproceso de J2 (`kill -9`), el proceso del daemon **no termina ni se reinicia** (conserva su PID).
4. Los subprocesos de J1 y J3 **permanecen vivos en el SO** y sus estados en el daemon continúan reportándose como `Running` (cumplimiento de **RNF-09**).
5. El daemon rechaza solicitudes inválidas sin caerse y responde satisfactoriamente a `health` tras los fallos (cumplimiento de **RNF-08**).
6. Al concluir el caso no se registran procesos zombis ni procesos residuales huérfanos.

### FAIL

1. El daemon termina, se bloquea o se reinicia tras enviar `kill -9` a J2 (violación de RNF-08 / RNF-09).
2. Los procesos de J1 o J3 mueren o se interrumpen como consecuencia de la muerte de J2 (violación de RNF-09).
3. El estado de J1 o J3 en el daemon pasa indebidamente a un estado de error o interrupción tras matar a J2 (violación de RNF-09).
4. Una solicitud inválida provoca la caída del daemon (violación de RNF-08).
5. El daemon deja de responder al comando `health` tras el incidente (violación de RNF-08).
6. Quedan procesos zombi persistentes bajo el PID del daemon.

### BLOCKED

- El daemon no pudo iniciarse o no cargó la configuración esperada (`max_current=3`).
- Las utilidades del sistema requeridas (`kill`, `pgrep`) no están disponibles en el entorno.
