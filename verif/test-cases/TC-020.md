# TC-020 — Terminación inesperada del proceso hijo

## 1. Identificación

| Campo | Valor |
| ------- | ------- |
| **ID** | TC-020 |
| **Título** | Terminación inesperada del proceso hijo |
| **Prioridad** | Crítica |
| **Método** | Prueba |
| **Tipo** | Robustez / Integración / Gestión de Procesos |
| **Requisitos** | RF-29, RNF-30 |
| **Estado** | Pendiente |

## 2. Objetivo

Verificar el comportamiento del sistema cuando un proceso hijo en ejecución es terminado de forma abrupta e inesperada por una señal externa (`SIGKILL` / `kill -9`), conforme a los requisitos **RF-29** y **RNF-30**:

1. **RF-29 (Detección, liberación y diagnóstico tras muerte inesperada):** Si un proceso hijo termina inesperadamente, el daemon debe detectar el evento de forma asíncrona, cosechar el proceso (*reap*) evitando que quede como proceso zombi (`STAT Z` / `defunct`), liberar la ranura de concurrencia y registrar un estado terminal coherente con información de diagnóstico (estado `Failed` y registro de código de salida / terminación por señal).
2. **RNF-30 (Ausencia de procesos huérfanos o zombis tras fallo):** Tras la terminación inesperada o forzada del trabajo, el sistema no debe dejar procesos huérfanos ni zombis bajo su responsabilidad en el sistema operativo.

> Los resultados esperados se derivan de **RF-29** y **RNF-30**, garantizando que el recolector de procesos y el ciclo de vida del scheduler gestionan correctamente la muerte no controlada de subprocesos.

## 3. Precondiciones

1. El proyecto debe compilar correctamente (`cargo build`). El script usa el binario generado en `target/debug/speedyG`.
2. El script de verificación debe tener permisos de ejecución (`verif/scripts/TC-020.sh`).
3. Socket Unix y directorio de datos temporales aislados por corrida (`setup_run_env`), con persistencia explícita en `SPEEDYG_DB` o `SPEEDYG_JSON`.
4. El daemon se inicia con parámetros explícitos de prueba:

```bash
speedyG --socket <socket-temporal> --data-dir <datos-temporales> --max-current 1 --queue-cap 5
```

5. El script verifica en `daemon.log` que la configuración efectiva coincide con la solicitada (`max_current=1`, `queue_cap=5`); en caso contrario, el caso queda **BLOCKED**.
6. Se dispone de utilidades del sistema (`pgrep`, `kill`, `ps`) para rastrear procesos e inyectar señales.

## 4. Datos de prueba

| Identificador | Comando | Estado inicial | Papel en la prueba | Requisito evaluado |
| --- | --- | --- | --- | --- |
| **J1** | `sleep 2001` | `Running` | **Trabajo víctima:** Subproceso hijo que será terminado abruptamente con `kill -9` | RF-29, RNF-30 |
| **J2** | `echo siguiente-tras-muerte` | `Queued` | **Trabajo en cola:** Debe avanzar automáticamente a `Running → Succeeded` al liberarse la ranura | RF-29 |

### 4.1 Parámetros temporales

| Parámetro | Valor |
| --- | --- |
| Concurrencia máxima (`max_current`) | `1` |
| Tiempo de estabilización de J1 en `Running` | 2 s |
| Señal enviada a J1 | `SIGKILL` (`kill -9 <PID_J1>`) |
| Tiempo máximo de detección y cosecha del proceso | ≤ 3 s |
| Tiempo máximo para que J2 complete su ejecución | ≤ 5 s |
| Timeout total del caso | 45 s |

## 5. Procedimiento

1. Compilar el proyecto con `cargo build`.
2. Ejecutar `./verif/scripts/TC-020.sh`.
3. Iniciar el daemon en un entorno temporal aislado con `--max-current 1 --queue-cap 5`.
4. Registrar el PID del daemon y validar que se cargó la configuración esperada (`daemon-pid.txt`).
5. **Fase 1 — Lanzamiento de trabajos:**
   - Enviar trabajo víctima J1 (`sleep 2001`).
   - Enviar trabajo en cola J2 (`echo siguiente-tras-muerte`).
   - Esperar 2 s a que J1 pase a `Running` y J2 quede en `Queued`.
   - Consultar `status` consolidado y registrar estados iniciales (`status-pre-kill.txt`).
6. **Fase 2 — Identificación de PID en el SO:**
   - Localizar el PID del subproceso asociado a J1 (`pgrep -f "sleep 2001"`).
   - Registrar los PIDs en `pids-pre-kill.txt`.
7. **Fase 3 — Inyección de muerte inesperada (kill -9):**
   - Enviar `kill -9` directamente al PID del subproceso J1.
   - Registrar el evento en `kill-event.log`.
8. **Fase 4 — Verificación de detección y estado terminal con diagnóstico (RF-29):**
   - Esperar 2 s tras el kill.
   - Consultar `status <ID_J1>` y registrar el estado en `status-j1-post-kill.txt`.
   - Verificar que J1 pasó a un estado terminal coherente (`Failed` con código de salida / señal registrada).
   - Verificar que J2 avanzó a `Running` y culminó exitosamente en `Succeeded` con código `0` (`status-j2-post-kill.txt`).
9. **Fase 5 — Verificación de ausencia de procesos zombis y huérfanos (RNF-30):**
   - Inspeccionar el estado de los procesos hijos bajo el PID del daemon con `ps` (`zombies-check.txt`).
   - Comprobar que no existen procesos con estado `STAT Z` (`defunct`).
   - Comprobar que no existen procesos huérfanos con el comando `sleep 2001`.
10. **Fase 6 — Cierre y verificación de salud:**
    - Consultar `health` del daemon y verificar que responde `OK` (`health-check.txt`).
    - Detener el daemon y concluir el caso.

## 6. Resultados esperados

### RF-29 — Detección, liberación y diagnóstico

- El daemon detecta la terminación súbita de J1 sin caerse ni entrar en *panic*.
- El estado de J1 transiciona a un estado terminal de fallo (`Failed`).
- La ranura de ejecución se libera inmediatamente, permitiendo que J2 avance a `Running` y termine `Succeeded` con exit code `0`.
- El daemon responde `health` correctamente.

### RNF-30 — Ausencia de zombis y huérfanos

- El subproceso de J1 es cosechado (*reaped*) por el runtime del daemon; **no queda ningún proceso en estado `STAT Z`**.
- Ningún proceso residual de `sleep 2001` permanece en ejecución en el sistema operativo.

## 8. Criterios PASS/FAIL/BLOCKED

### PASS

Se cumplen **todos** los siguientes criterios:

1. El daemon inicia y carga la configuración solicitada (`max_current=1`, `queue_cap=5`).
2. J1 entra en `Running` y J2 queda en `Queued`.
3. Al enviar `SIGKILL` a J1, el daemon permanece activo y detecta la terminación.
4. J1 pasa a estado terminal de fallo (`Failed`) y su diagnóstico refleja la señal de terminación o código POSIX 137 (no solo un -1 genérico) (RF-29).
5. J2 avanza automáticamente a `Running` y culmina en `Succeeded` con código `0` (RF-29).
6. No se detectan procesos zombis (`STAT Z`) bajo el PID del daemon ni en el sistema operativo (RNF-30).
7. No quedan procesos residuales asociados a `sleep 2001` (RNF-30).
8. El daemon responde satisfactoriamente a `health`.

### FAIL

1. J1 permanece reportado como `Running` tras morir en el SO (violación de RF-29).
2. J1 no registra la señal en su diagnóstico o solo reporta -1 sin información de terminación por señal (violación de RF-29).
2. J2 no avanza tras liberarse la ranura de concurrencia (violación de RF-29).
3. Se detectan procesos en estado zombi (`STAT Z` / `defunct`) bajo el daemon (violación de RNF-30).
4. Quedan procesos huérfanos de `sleep 2001` en el sistema operativo (violación de RNF-30).
5. El daemon termina o se reinicia de forma no controlada ante la muerte del subproceso (violación de RF-29).

### BLOCKED

- El daemon no pudo iniciarse o no cargó la configuración esperada (`max_current=1`).
- Las utilidades del sistema (`kill`, `pgrep`, `ps`) no están disponibles en el entorno.
