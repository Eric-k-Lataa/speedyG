## 2. Objetivo

Verificar que una solicitud duplicada o reenviada no crea estados contradictorios y que el servicio aplica la semántica documentada (RF-27).

**Semántica elegida (ADR-04, decisión 2):** las solicitudes duplicadas se tratan como **trabajos independientes**. Cada solicitud recibida crea un trabajo nuevo, aunque tenga exactamente el mismo comando que otra anterior. No existe detección de duplicados ni `request-id`.

Consecuencia que debe cumplirse y que este caso comprueba:

1. N solicitudes idénticas producen N trabajos con N identificadores distintos.
2. Cada trabajo tiene su propio ciclo de vida: ninguno comparte estado, código de salida ni proceso con otro.
3. Lo anterior vale tanto para envíos secuenciales como concurrentes.
4. Cancelar un trabajo no afecta a sus duplicados.
5. Ningún envío se pierde ni se fusiona con otro.

> El caso verifica la semántica **documentada**. Si el equipo cambia la decisión del ADR-04 (por ejemplo, a `request-id`), este caso debe reescribirse. Los resultados esperados se derivan de RF-27 y del ADR-04, no del comportamiento observado del código.

## 3. Precondiciones

1. El proyecto debe compilar (`cargo build`). El script usa `target/debug/`.
2. El script debe tener permisos de ejecución (`verif/scripts/TC-018.sh`).
3. Socket Unix y directorio de datos temporales y propios de la corrida; persistencia aislada con `SPEEDYG_DB` y `SPEEDYG_JSON`.
4. El daemon se inicia con parámetros explícitos:

```bash
speedyG --socket <socket-temporal> --data-dir <datos-temporales> --max-current 4 --queue-cap 30
```

5. El script comprueba en `daemon.log` que `max_current=4` y `queue_cap=30`; si no, el caso queda **BLOCKED**.
6. Los trabajos con marcador `echo dup-` terminan de forma natural; los de `sleep` se cancelan al final del escenario D.

## 4. Datos de prueba

### 4.1 Escenarios

| Escenario | Solicitudes | Descripción |
| --- | --- | --- |
| A | 5 × `echo dup-A` secuenciales | Duplicados exactos, uno tras otro |
| B | 10 × `echo dup-B` concurrentes (`&` y `wait`) | Duplicados exactos simultáneos |
| C | 1 × `echo dup-C` enviado dos veces, la segunda tras ver la respuesta de la primera | Reenvío tras confirmación (simula un cliente que reintenta) |
| D | 3 × `sleep 3001` | Duplicados que permanecen vivos; se cancela solo el segundo |

### 4.2 Parámetros

| Parámetro | Valor |
| --- | --- |
| Tiempo máximo de respuesta por envío | 10 s |
| Tiempo máximo para que todos los `echo` terminen | 30 s |
| Tiempo máximo del caso | 90 s |

## 5. Procedimiento

1. Ejecutar `cargo build` y `./verif/scripts/TC-018.sh`.
2. El script crea el entorno, arranca el daemon y valida la configuración.
3. **Escenario A:** envía 5 veces `echo dup-A`, una tras otra, y registra cada respuesta.
4. **Escenario B:** lanza 10 clientes a la vez con `echo dup-B` (`&` y `wait`) y registra cada respuesta.
5. **Escenario C:** envía `echo dup-C`, registra el ID devuelto y lo reenvía idéntico.
6. Espera a que los 17 `echo` terminen y consulta `status`.
7. **Escenario D:** envía 3 veces `sleep 3001`, comprueba que los 3 son trabajos distintos con su propio proceso, cancela solo el segundo y comprueba que el primero y el tercero siguen sin cambios; luego los cancela.
8. Comprueba `health`, que no hay procesos con el marcador `sleep 3001` y que no quedan hijos ni zombis del daemon.

## 6. Resultados esperados

### RF-27 — Cada solicitud es un trabajo independiente

Para cada escenario:

- **Todas** las solicitudes devuelven `Job #N encolado correctamente`; ninguna se rechaza como duplicada ni devuelve el ID de otra.
- Los IDs devueltos son **todos distintos** (A: 5, B: 10, C: 2, D: 3).
- El listado `status` contiene exactamente un trabajo por solicitud aceptada (total esperado: 5 + 10 + 2 + 3 = 20), sin trabajos repetidos y sin trabajos faltantes.
- Cada trabajo conserva el comando exacto enviado.

### RF-27 — Sin estados contradictorios

- Los 17 trabajos `echo` terminan en `Succeeded` con `exit code: 0`, cada uno con su propio registro.
- No hay dos trabajos con el mismo ID ni un mismo ID con dos estados distintos en una misma consulta.
- En las muestras de estado no hay regresiones (`Running → Queued`) ni cambios entre estados terminales.

### Aislamiento entre duplicados (escenario D)

- Los 3 `sleep 3001` son trabajos distintos y cada uno tiene su propio proceso en el sistema operativo (3 procesos con el marcador, uno por trabajo).
- Cancelar el segundo lo deja en `Canceled` y su proceso desaparece en 5 s.
- El primero y el tercero **siguen en `Running`** y sus procesos siguen vivos tras la cancelación.

### RNF-27 — Consistencia

- Tras los envíos concurrentes del escenario B, los IDs son únicos y el listado es consistente con las respuestas recibidas.
- El daemon responde `health` al final.

## 8. Criterios PASS/FAIL/BLOCKED

### PASS

Se cumplen **todos** los criterios:

1. El daemon cargó `max_current=4` y `queue_cap=30`.
2. Las 20 solicitudes son aceptadas con 20 IDs distintos.
3. `status` lista exactamente 20 trabajos, sin repetidos ni faltantes, con el comando enviado.
4. Los 17 `echo` terminan `Succeeded` con exit code 0.
5. Los 3 `sleep 3001` tienen cada uno su proceso; cancelar el segundo no afecta al primero ni al tercero.
6. No hay regresiones ni estados contradictorios en las muestras.
7. El daemon responde `health` y no quedan procesos huérfanos ni zombis.

### FAIL

1. Una solicitud duplicada se rechaza, se fusiona con otra o devuelve un ID ya usado.
2. Faltan o sobran trabajos respecto de las solicitudes aceptadas.
3. Dos trabajos comparten ID, estado o proceso.
4. Cancelar un duplicado afecta a otro.
5. Hay estados contradictorios o regresiones.
6. El daemon deja de responder o quedan procesos huérfanos o zombis.

### BLOCKED

El daemon no cargó la configuración esperada o no pudo iniciarse.

> **Nota sobre ADR-04, riesgos:** el propio ADR advierte que aceptar duplicados puede ejecutar varias veces un mismo comando. Este caso verifica que el comportamiento es el documentado y coherente; no valida que sea el más seguro para el usuario.
