# TC-006 — Capturar stdout/stderr y código

## 1. Identificación

| Campo | Valor |

| **Prioridad** | Crítica |

## 2. Objetivo

Verificar que el sistema speedyG captura y almacena de forma fidedigna y desacoplada las salidas de ejecución de los procesos y sus códigos de finalización:

1. **RF-11 (Separación de salidas):** El sistema debe capturar la salida estándar (`stdout`) y el error estándar (`stderr`) en canales independientes, garantizando que no se mezclen, intercalen ni contaminen entre sí, y permitiendo su consulta detallada mediante `status <id>`.
2. **RF-07 (Código de salida y marcas temporales):** El sistema debe registrar con precisión el código de retorno (*exit code*) del proceso al finalizar (éxito `0` o fallo `≠ 0`) y los tiempos de recepción, inicio y terminación.
3. **Manejo de salidas voluminosas:** El sistema debe capturar salidas de gran tamaño (múltiples kilobytes / 1000 líneas) sin saturar los pipes del sistema operativo, sin provocar bloqueos (*deadlocks*) en el daemon y sin truncar el contenido capturado.
4. **Comandos no ejecutables / inexistentes:** Cuando se invoque un binario inexistente o no ejecutable, el error del sistema operativo debe canalizarse apropiadamente hacia `stderr` marcando el trabajo como `Failed`.

> Los resultados esperados se derivan directamente de RF-07, RF-11 y del estándar de comunicación del proyecto speedyG.

## 3. Precondiciones

1. El proyecto debe compilar (`cargo build`). El script usa `target/debug/speedyG`.
2. El script de verificación debe tener permisos de ejecución (`verif/scripts/TC-006.sh`).
3. Socket Unix y directorio de datos temporales aislados por corrida (`setup_run_env`), con persistencia explícita en `SPEEDYG_DB` o `SPEEDYG_JSON`.
4. El daemon se arranca con parámetros controlados:

```bash
speedyG --socket <socket-temporal> --data-dir <datos-temporales> --max-current 2 --queue-cap 10
```

5. El script comprueba en `daemon.log` que la configuración fue cargada (`max_current=2`, `queue_cap=10`); si no, el caso queda **BLOCKED**.

## 4. Datos de prueba

Se definen casos de prueba especializados para evaluar cada canal de salida y escenarios límite:

| Clave | Comando | Salida esperada en stdout | Salida esperada en stderr | Exit Code | Estado |
| :--- | :--- | :--- | :--- | :---: | :---: |
| **J1_OUT** | `echo "SOLO_STDOUT_LINEA_1"` | `SOLO_STDOUT_LINEA_1` | *(vacío)* | `0` | `Succeeded` |
| **J2_ERR** | `sh -c 'echo "SOLO_STDERR_LINEA_1" >&2'` | *(vacío)* | `SOLO_STDERR_LINEA_1` | `0` | `Succeeded` |
| **J3_MIX** | `sh -c 'echo "OUT_CANAL_1"; echo "ERR_CANAL_2" >&2'` | `OUT_CANAL_1` | `ERR_CANAL_2` | `0` | `Succeeded` |
| **J4_FAIL** | `sh -c 'echo "MSG_FAIL_ERR" >&2; exit 42'` | *(vacío)* | `MSG_FAIL_ERR` | `42` | `Failed` |
| **J5_BIG** | `sh -c 'for i in $(seq 1 1000); do echo "LINEA_BIG_$i"; done'` | 1000 líneas (`LINEA_BIG_1` … `LINEA_BIG_1000`) | *(vacío)* | `0` | `Succeeded` |
| **J6_NOENT** | `binario_inexistente_speedyg_test_xyz` | *(vacío)* | Mensaje de error del SO (*No such file / no encontrado*) | *(≠ 0)* | `Failed` |

### 4.1 Parámetros temporales

| Parámetro | Valor |
| --- | --- |
| Tiempo máximo de ejecución para J1..J4 | ≤ 3 s por trabajo |
| Tiempo máximo de ejecución para J5 (salida grande) | ≤ 10 s |

| Timeout total del caso | 45 s |

## 5. Procedimiento

1. Compilar el proyecto con `cargo build`.
2. Ejecutar `./verif/scripts/TC-006.sh`.
3. Iniciar el demonio `speedyG` en un ambiente aislado.
4. **Paso 1 — Salida estándar exclusiva (J1_OUT):**
   - Enviar `echo "SOLO_STDOUT_LINEA_1"`.
   - Esperar estado `Succeeded`.
   - Consultar `status <id>` y verificar que la sección `[stdout]` contiene el texto y la sección `[stderr]` no aparece o está vacía.
5. **Paso 2 — Error estándar exclusivo (J2_ERR):**
   - Enviar comando redirigiendo a descriptor 2 (`>&2`).
   - Esperar estado `Succeeded`.
   - Consultar `status <id>` y verificar que `[stderr]` contiene el mensaje y `[stdout]` no contiene contenido espurio.
6. **Paso 3 — Salidas simultáneas no mezcladas (J3_MIX):**
   - Enviar comando que escribe simultáneamente a stdout y stderr.
   - Esperar estado `Succeeded`.
   - Verificar que `[stdout]` contiene exclusivamente `OUT_CANAL_1` y `[stderr]` contiene exclusivamente `ERR_CANAL_2`.
7. **Paso 4 — Código de salida distinto de cero (J4_FAIL):**
   - Enviar comando que emite mensaje de error y termina con código `42`.
   - Esperar estado `Failed`.
   - Verificar que `exit code: 42` es reportado explícitamente y el mensaje de error está en `[stderr]`.
8. **Paso 5 — Salida voluminosa / Buffer grande (J5_BIG):**
   - Enviar comando generador de 1000 líneas secuenciales.
   - Esperar a que el trabajo concluya con éxito sin colgar el daemon.
   - Validar que se recibieron las 1000 líneas completas, verificando la primera línea (`LINEA_BIG_1`), la última (`LINEA_BIG_1000`) y el conteo de líneas total.
9. **Paso 6 — Comando inexistente (J6_NOENT):**
   - Enviar llamada a un comando que no existe en el `PATH`.
   - Verificar que el estado resultante es `Failed` y que el motivo del fallo se reporta en `[stderr]`.
10. **Paso 7 — Detención y reporte:**
    - Detener el daemon de forma limpia, comprobar ausencia de procesos zombis y compilar evidencias.

## 6. Resultados esperados

### RF-11 — Captura de stdout y stderr y consulta

- `status <J1>` muestra bloque `[stdout]:` indentado con `SOLO_STDOUT_LINEA_1` y **no** contiene bloque `[stderr]:`.
- `status <J2>` muestra bloque `[stderr]:` indentado con `SOLO_STDERR_LINEA_1` y **no** contiene bloque `[stdout]:`.
- `status <J3>` muestra ambos bloques debidamente separados:
  ```text
  [stdout]:
      OUT_CANAL_1
  [stderr]:
      ERR_CANAL_2
  ```
  En ningún caso el texto de stdout se fuga a stderr ni viceversa.
- `status <J5>` entrega las 1000 líneas generadas íntegras en `[stdout]` sin truncamiento ni corrupción de caracteres.

### RF-07 — Registro de tiempos: recepción, inicio y terminación, así como código de salida

- `status <J1>` indica `(exit code: 0)`.
- `status <J4>` indica `(exit code: 42)` y clasifica el trabajo como `Failed`.
- Toda consulta detallada preserva los timestamps válidos:
  - `Recibido:` formato `%Y-%m-%d %H:%M:%S UTC`
  - `Iniciado:` formato `%Y-%m-%d %H:%M:%S UTC`
  - `Finalizado:` formato `%Y-%m-%d %H:%M:%S UTC`
  - Cumpliendo la relación de orden cronológico: `Recibido ≤ Iniciado ≤ Finalizado`.

## 8. Criterios PASS/FAIL/BLOCKED

### PASS

Se cumplen **todos** los siguientes criterios:

1. El daemon inició y cargó la configuración (`max_current=2`, `queue_cap=10`).
2. `stdout` y `stderr` son capturados en canales independientes y mostrados en sus secciones correspondientes sin contaminación cruzada.
3. El código de salida `0` se reporta en éxitos y el código `42` se reporta exactamente en `J4_FAIL`.
4. La salida voluminosa de 1000 líneas es capturada íntegra sin bloqueos en los pipes ni truncamiento de datos.
5. El comando inexistente se clasifica como `Failed` con el error en `[stderr]`.
6. Las marcas temporales (`Recibido`, `Iniciado`, `Finalizado`) están presentes y cumplen el orden cronológico.
7. Al concluir la prueba no quedan procesos zombis ni procesos residuales.

### FAIL

1. `stdout` y `stderr` aparecen mezclados en el mismo canal o invertidos.
2. Un trabajo exitoso no reporta `exit code: 0` o un trabajo fallido pierde su código de error real (ej. `42`).
3. El daemon se bloquea (*deadlock*) o trunca el contenido al recibir una salida grande en `stdout`/`stderr`.
4. Un comando inexistente se marca como `Succeeded` o se pierden los mensajes de error del sistema operativo.
5. Las marcas temporales no existen o violan la cronología.
6. Se detectan procesos zombis o fugas de file descriptors.

### BLOCKED

- El daemon no pudo iniciarse o no cargó la configuración solicitada.
- El shell `/bin/sh` no está disponible en el entorno para las pruebas de redirección de descriptores.
