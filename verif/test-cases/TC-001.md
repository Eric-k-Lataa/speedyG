## 2. Objetivo

Verificar el flujo de recepción y ejecución de un trabajo mediante el servicio `speedyG`.

El caso comprueba que una solicitud válida sea aceptada, reciba un identificador, sea registrada por el `Scheduler` y pueda iniciar y finalizar su ejecución.

También se comprueba que una solicitud no autorizada sea rechazada mediante un mensaje de error útil y que el servicio continúe disponible después del rechazo.

## 3. Precondiciones

1. El proyecto debe compilar correctamente.
2. El daemon `speedyG` debe poder iniciarse.
3. El socket Unix `/tmp/speedyg.sock` debe estar disponible.
4. El cliente `speedyg` debe poder conectarse al socket.
5. No debe existir una instancia previa del daemon utilizando el mismo socket.
6. El script `verif/scripts/TC-001.sh` debe tener permisos de ejecución.

## 5. Procedimiento

1. Iniciar el daemon en una terminal:

   ```bash
   cargo run --bin speedyG
   ```

2. Desde una segunda terminal, ejecutar el script de verificación:

   ```bash
   ./verif/scripts/TC-001.sh
   ```

3. El script envía la solicitud válida:

   ```bash
   cargo run --bin speedyg -- echo hola
   ```

4. Verificar que el cliente reciba una respuesta con el identificador del trabajo.

5. Consultar el estado del trabajo mediante:

   ```bash
   cargo run --bin speedyg -- status <ID>
   ```

6. Enviar el comando de ejecución prolongada:

   ```bash
   cargo run --bin speedyg -- sleep 10
   ```

7. Consultar el estado del trabajo mientras se encuentra en ejecución y verificar que aparezca como `Running`.

8. Esperar la finalización del trabajo y verificar que termine correctamente.

9. Enviar un comando no autorizado:

   ```bash
   cargo run --bin speedyg -- rm archivo.txt
   ```

10. Verificar que la solicitud sea rechazada y que el daemon continúe disponible mediante:

```bash
cargo run --bin speedyg -- health
```

## 6. Resultados esperados

### RF-01 — Enviar trabajo e ID único

El sistema debe aceptar la solicitud válida y devolver un identificador asociado al trabajo.

**Criterios de aceptación:**

* La solicitud válida es aceptada.
* Se genera un identificador para el trabajo.
* El identificador se devuelve al cliente.
* El trabajo queda registrado en el `Scheduler`.
* El trabajo puede ser consultado mediante `status`.

### RF-02 — Validar solicitud con mensaje útil

El sistema debe rechazar la solicitud no autorizada.

**Criterios de aceptación:**

* La solicitud es rechazada.
* Se informa al cliente de la causa del rechazo.
* La solicitud rechazada no genera un trabajo válido.
* El daemon continúa disponible después del rechazo.

### RF-04 — Procesos independientes

El trabajo aceptado debe ejecutarse independientemente del procesamiento de la conexión del cliente.

**Criterios de aceptación:**

* El cliente recibe la respuesta de encolamiento antes de que termine la ejecución del trabajo.
* El trabajo puede observarse en estado `Running`.
* El trabajo posteriormente alcanza el estado `Succeeded`.
* El trabajo es ejecutado por el `Executor`.

> Nota: en esta ejecución se verificó el estado `Running`, pero no se realizó una captura mediante `ps`. Por lo tanto, no se registra evidencia de identificación del proceso mediante `ps`.

## 8. Criterios PASS/FAIL

### PASS

El caso se considera `PASS` cuando:

1. La solicitud válida es aceptada.
2. Se devuelve un identificador de trabajo.
3. El trabajo puede ser consultado mediante `status`.
4. El trabajo puede observarse en estado `Running`.
5. El trabajo finaliza correctamente.
6. La solicitud no autorizada es rechazada con un mensaje útil.
7. El servicio continúa disponible después del rechazo.

La identificación del proceso mediante `ps` no forma parte del criterio obligatorio de PASS de esta ejecución, debido a que dicha evidencia no fue recopilada.

### FAIL

El caso se considera `FAIL` cuando alguno de los criterios de aceptación establecidos para RF-01, RF-02 o RF-04 no se cumple.

El incumplimiento debe registrarse como defecto o excepción en la evidencia de ejecución.
