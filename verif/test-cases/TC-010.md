## 2. Objetivo

Verificar que el daemon admite comunicación remota mediante TCP desde un cliente ubicado en la misma red privada o conectado por VPN, permitiendo ejecutar las operaciones soportadas por el protocolo (`health`, `submit`, `status`, `list` y `cancel`) y obteniendo la misma semántica observable que al acceder mediante Unix Domain Socket local (RF-19).

Asimismo, verificar que la demostración remota se realiza exclusivamente dentro de una LAN o VPN privada, sin requerir exposición directa del puerto del servicio a Internet (RNF-26).

Configuración del caso (ADR-06):

- Socket Unix local habilitado.
- Listener TCP habilitado simultáneamente.
- Ambos transportes enrutan al mismo despachador interno.
- Mensajes delimitados mediante JSON finalizado con `\n`.
- Sin handshake previo.
- Mismo protocolo y mismas operaciones sobre ambos transportes.

> Los resultados esperados se derivan de RF-18, RF-19, RNF-26 y ADR-06, no del comportamiento observado del código.

## 3. Precondiciones

1. El proyecto debe compilar (`cargo build`). El script usa `target/debug/speedyG`.
2. El script de verificación debe tener permisos de ejecución (`verif/scripts/TC-010.sh`).
3. Socket Unix y directorio de datos temporales aislados por corrida (`setup_run_env`), con persistencia explícita en `SPEEDYG_DB` o `SPEEDYG_JSON`.
4. El daemon debe iniciarse con:
   - Socket Unix habilitado.
   - Listener TCP habilitado.
5. Debe existir conectividad entre cliente y servidor mediante:
   - Red LAN privada, o
   - VPN privada.
6. El cliente remoto debe poder alcanzar el puerto TCP configurado.
7. El servicio no debe estar expuesto directamente a Internet durante la prueba.
8. El daemon debe registrar correctamente su dirección TCP de escucha en `daemon.log`.

## 4. Datos de prueba

| Dato | Valor |
| --- | --- |
| Trabajo corto | `echo remoto_ok` |
| Trabajo largo | `sleep 20` |
| Operaciones remotas | `health`, `submit`, `status`, `list`, `cancel` |
| Operaciones locales de comparación | `submit`, `status` |
| Tiempo máximo de respuesta por operación | 5 s |
| Tiempo máximo del caso | 60 s |

El trabajo corto permite validar envío y ejecución exitosa.

El trabajo largo permite validar cancelación remota.

## 5. Procedimiento

1. Ejecutar `cargo build`.
2. Iniciar el daemon con Socket Unix y listener TCP habilitados.
3. Registrar dirección IP y puerto TCP utilizados.
4. Desde un cliente remoto ejecutar `health`.
5. Registrar la respuesta.
6. Desde el cliente remoto enviar:

```bash
echo remoto_ok
```

7. Registrar el ID asignado.
8. Consultar el trabajo mediante `status`.
9. Esperar a que finalice.
10. Consultar nuevamente `status`.
11. Ejecutar `list` y verificar que el trabajo aparece.
12. Enviar un segundo trabajo:

```bash
sleep 20
```

13. Registrar el ID asignado.
14. Consultar el trabajo mediante `status`.
15. Ejecutar `cancel`.
16. Registrar la respuesta.
17. Consultar nuevamente `status`.
18. Desde el mismo host del daemon ejecutar una consulta local mediante Unix Socket para uno de los trabajos creados.
19. Comparar la información obtenida por TCP y por Unix Socket.
20. Verificar que ambos accesos reportan el mismo estado del trabajo.
21. Revisar `daemon.log`.
22. Finalizar el daemon.

> La comparación del paso 19 verifica explícitamente RF-19: misma semántica independientemente del transporte utilizado.

## 6. Resultados esperados

### RF-18 — Un cliente en otro equipo deberá poder enviar, consultar, listar y cancelar trabajos mediante un protocolo documentado.

- El cliente remoto puede ejecutar `health`.
- El cliente remoto puede ejecutar `submit`.
- El cliente remoto puede ejecutar `status`.
- El cliente remoto puede ejecutar `list`.
- El cliente remoto puede ejecutar `cancel`.
- Todas las operaciones reciben respuestas válidas.

### RF-19 — El servicio deberá admitir operación local y remota sin cambiar la semántica de las operaciones.

- Un trabajo enviado remotamente recibe un ID válido igual que en operación local.
- Los estados observados mediante TCP coinciden con los observados mediante Unix Socket.
- Las respuestas representan la misma información independientemente del transporte.
- La cancelación realizada remotamente se refleja inmediatamente en consultas locales.
- No existen estados o comportamientos exclusivos de un transporte.

### RNF-26 — La demostración remota se realizará exclusivamente en la misma red privada o por VPN; no se aceptará exposición directa a Internet.

- La IP utilizada pertenece a una LAN privada o VPN.
- El puerto del servicio es accesible únicamente desde la red privada correspondiente.
- No se requiere publicar el servicio en Internet para completar el caso.
- La demostración puede ejecutarse completamente dentro de la red privada definida.

## 8. Criterios PASS/FAIL/BLOCKED

### PASS

Se cumplen **todos** los criterios:

1. El daemon acepta conexiones TCP remotas.
2. `health` responde correctamente.
3. Un cliente remoto puede enviar trabajos.
4. Un cliente remoto puede consultar trabajos.
5. Un cliente remoto puede listar trabajos.
6. Un cliente remoto puede cancelar trabajos.
7. Las consultas locales y remotas muestran información consistente para el mismo trabajo.
8. La cancelación remota es visible desde el acceso local.
9. El daemon permanece operativo durante toda la prueba.
10. No se requieren cambios de semántica entre Unix Socket y TCP.
11. La prueba se realiza completamente dentro de una LAN o VPN privada.
12. No existen errores críticos en `daemon.log`.

### FAIL

1. El cliente remoto no puede conectarse al listener TCP.
2. Alguna operación soportada falla (`health`, `submit`, `status`, `list`, `cancel`).
3. TCP y Unix Socket muestran resultados inconsistentes para el mismo trabajo.
4. La cancelación remota no se refleja correctamente.
5. El daemon deja de responder.
6. La ejecución requiere exponer el servicio a Internet.
7. Se detectan errores críticos del protocolo en `daemon.log`.

### BLOCKED

- El daemon no inicia correctamente.
- El listener TCP no queda disponible.
- No existe conectividad LAN o VPN entre cliente y servidor.
- No puede establecerse el entorno aislado requerido.
- No es posible verificar simultáneamente acceso Unix Socket y TCP.
