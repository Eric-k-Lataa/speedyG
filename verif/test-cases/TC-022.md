# TC-022 — Interrupción durante persistencia

## 1. Identificación

| Campo | Valor |
| ------- | ------- |
| **ID** | TC-022 |
| **Título** | Interrupción durante persistencia |
| **Prioridad** | Crítica |
| **Método** | Prueba |
| **Tipo** | Funcional / Integración |
| **Requisitos** | RNF-28, RNF-31 |
| **Estado** | Pendiente |

## 2. Objetivo

Verificar que una interrupción abrupta del servicio mientras guarda su estado (`kill -9` del daemon) no deja la persistencia inutilizable ni inconsistente (RNF-28), y que al reiniciar la recuperación distingue trabajos **pendientes**, **terminados** e **interrumpidos** sin reportar como `Running` un proceso que ya no existe (RNF-31).

El caso se divide en tres escenarios:

1. **Escenario A — Interrupción bajo carga de escritura.** Se mata el daemon con `SIGKILL` mientras recibe y ejecuta muchos trabajos (cada envío, inicio y término provoca una escritura). Se repite varias veces con retardos distintos, porque una interrupción exactamente durante una escritura es probabilística. Un solo intento sin fallo no demuestra ausencia de carreras.
2. **Escenario B — Clasificación tras reinicio.** Se prepara un estado determinista con un trabajo terminado, uno cancelado, uno en ejecución y dos pendientes, se mata el daemon y se verifica cómo los clasifica la recuperación.
3. **Escenario C — Archivos de persistencia dañados.** Se simulan los estados que una interrupción podría dejar en disco (archivo temporal parcial, JSON truncado, base de datos ilegible) y se verifica que el servicio arranca y recupera el estado desde la copia sana.

> Los resultados esperados se derivan de RNF-28, RNF-31 y del ADR-03, no del comportamiento observado del código. El ADR-03 reconoce como riesgo la pérdida o corrupción de información si ocurre una interrupción durante una escritura.

## 3. Precondiciones

1. El proyecto debe compilar (`cargo build`). El script usa `target/debug/speedyG`.
2. El script de verificación debe tener permisos de ejecución (`verif/scripts/TC-022.sh`).
3. Socket Unix y directorio de datos temporales aislados por corrida (`setup_run_env`), con persistencia explícita en `SPEEDYG_DB` o `SPEEDYG_JSON`.
4. El daemon se inicia con parámetros explícitos. Los escenarios A y C usan `--max-current 4 --queue-cap 30`; el B usa `--max-current 1 --queue-cap 10`:

```bash
speedyG --socket <socket-temporal> --data-dir <datos-temporales> --max-current 4 --queue-cap 30
```

5. El script comprueba en `daemon.log` que la configuración efectiva coincide con la solicitada; si no, el caso queda **BLOCKED**.
6. En cada reinicio se usa **el mismo** socket, directorio de datos, `SPEEDYG_DB` y `SPEEDYG_JSON` que antes de la interrupción.
7. Para el chequeo de integridad de la base se necesita el cliente `sqlite3` y, para validar el JSON, `python3`. Si alguno no está disponible, solo esa comprobación se registra como **BLOCKED** y el resto del caso continúa.
8. **Dependencias de implementación:** la persistencia en SQLite/JSON y la recuperación tras reinicio (RF-12, RF-13). Si existen pero el comportamiento observado es incorrecto, el resultado es **FAIL**, no BLOCKED.

> `kill -9` sobre el daemon no termina a los procesos de los trabajos en ejecución: quedan huérfanos. Al terminar cada escenario el script los elimina por su marcador (`sleep 100<n>`) para no contaminar el siguiente. Que queden huérfanos tras una caída **no se evalúa aquí** (RNF-30, TC-009 y TC-020).

## 4. Datos de prueba

### 4.1 Escenario A — Interrupción bajo carga

| Dato | Valor |
| --- | --- |
| Iteraciones | 10 |
| Trabajos por iteración | 20 × `echo carga-<iteración>-<n>`, enviados en paralelo con `&` |
| Retardo hasta `kill -9` | 0,05 s a 0,40 s tras lanzar los envíos, distinto en cada iteración (por ejemplo, 0,05 + 0,035 × iteración) |
| Registro de aceptados | Solo se consideran aceptados los IDs cuya respuesta contenía `encolado correctamente` antes del `kill -9` |
| Espera tras reiniciar | 30 s máximo hasta que no quede ningún trabajo `Queued` ni `Running` |
| Reinicios | El daemon se reinicia en la misma carpeta de datos en cada iteración (la numeración de IDs y el historial continúan entre iteraciones) |

### 4.2 Escenario B — Clasificación tras reinicio

Daemon con `--max-current 1 --queue-cap 10`. Los trabajos se envían en este orden y cada uno se lleva al estado indicado antes de enviar el siguiente:

| Trabajo | Comando | Estado antes de `kill -9` | Estado esperado tras reiniciar |
| --- | --- | --- | --- |
| D | `echo terminado` | `Succeeded`, exit code 0 | `Succeeded`, exit code 0, sin cambios |
| E | `sleep 1005` (se cancela) | `Canceled` | `Canceled`, sin cambios |
| A | `sleep 1003` | `Running` | `Interrupted` |
| B | `sleep 2` | `Queued` | `Succeeded` (se relanza y termina) |
| C | `echo pendiente` | `Queued` | `Succeeded` (se relanza tras B) |

Los comandos `sleep 1003` y `sleep 1005` llevan un argumento único para localizar sus procesos en el sistema operativo.

### 4.3 Escenario C — Archivos dañados

Línea base: el daemon (`--max-current 4 --queue-cap 30`) recibe dos `echo` que terminan en `Succeeded` y un `sleep 1006` que se cancela (`Canceled`). Se mata el daemon con `kill -9` en reposo y se guarda una copia de la carpeta de datos (`speedyg.db`, `speedyg.db-wal`/`-shm` si existen, `scheduler.json`). Antes de cada sub-escenario se restaura esa copia.

| Sub-escenario | Daño aplicado | Qué debe ocurrir |
| --- | --- | --- |
| C1 | Se crea `scheduler.json.tmp` con la mitad del contenido de `scheduler.json` (escritura interrumpida antes del `rename`) | El estado recuperado es idéntico a la línea base |
| C2 | `scheduler.json` truncado a la mitad; la base SQLite intacta | El estado recuperado es idéntico a la línea base |
| C3 | `speedyg.db` sobrescrito con bytes no válidos (misma ubicación, mismo nombre); `scheduler.json` intacto | El estado recuperado es idéntico a la línea base y la recuperación queda registrada en `daemon.log`. Tras recuperar, un trabajo nuevo se acepta y **sobrevive a un nuevo `kill -9` y reinicio** |
| C4 | Base y JSON ilegibles | El daemon no se cae, responde `health`, registra el error en `daemon.log` y no inventa trabajos |

### 4.4 Parámetros

| Parámetro | Valor |
| --- | --- |
| Espera de socket tras reiniciar | 10 s (`DAEMON_WAIT_SECS`) |
| Tiempo máximo de respuesta de `status` tras reiniciar | 3 s |
| Tiempo máximo de recuperación de pendientes (escenarios A y B) | 30 s |
| Tiempo máximo del caso | 180 s |

## 5. Procedimiento

1. Ejecutar `cargo build` y `./verif/scripts/TC-022.sh`.
2. El script crea el entorno, arranca el daemon y valida la configuración (sección 3).

**Escenario A**

3. Por cada una de las 10 iteraciones:
   1. Lanzar 20 envíos `echo` en paralelo, guardando para cada uno su respuesta.
   2. Esperar el retardo de la iteración y enviar `SIGKILL` al PID del daemon.
   3. Esperar a que terminen los clientes y registrar los IDs aceptados.
   4. Comprobar la integridad de `speedyg.db` (`PRAGMA integrity_check`) y que `scheduler.json`, si existe, es JSON válido.
   5. Reiniciar el daemon con los mismos parámetros y registrar el tiempo hasta que el socket responde.
   6. Consultar `status` y verificar los criterios de la sección 6.
   7. Esperar hasta 30 s a que no queden trabajos `Queued` ni `Running` y registrar el listado final.
   8. Enviar un trabajo `echo nuevo` y verificar que su ID es mayor que cualquier ID existente.

**Escenario B**

4. Reiniciar el entorno con `--max-current 1 --queue-cap 10`.
5. Enviar D y esperar a `Succeeded`. Enviar E (`sleep 1005`), esperar a `Running` y cancelarlo; verificar `Canceled` y que su proceso desapareció.
6. Enviar A (`sleep 1003`) y esperar a `Running`. Enviar B y C, que quedan `Queued`.
7. Guardar `status` de D, E, A, B y C (`before-<id>.txt`).
8. Enviar `SIGKILL` al daemon, eliminar los procesos huérfanos por su marcador y reiniciar el daemon.
9. Guardar `status` inmediatamente tras responder el socket (`after-<id>.txt`) y registrar el estado de A, B y C.
10. Esperar hasta 30 s a que B y C lleguen a `Succeeded`. Guardar el estado final.

**Escenario C**

11. Construir la línea base y guardar la copia de la carpeta de datos (sección 4.3).
12. Para cada sub-escenario C1 a C4: restaurar la copia, aplicar el daño, reiniciar el daemon y comparar `status` de cada trabajo con la línea base.
13. En C3, tras recuperar, enviar un trabajo nuevo, esperar a `Succeeded`, enviar `SIGKILL`, reiniciar y comprobar que el trabajo sigue presente.
14. En C4, comprobar `health`, el contenido de `status` y las entradas de error en `daemon.log`.

**Cierre**

15. Comprobar que el daemon responde `health`, eliminar los procesos huérfanos de los marcadores, detener el daemon y registrar el resultado.

## 6. Resultados esperados

### RNF-28 — Actualizaciones persistentes atómicas o recuperables

**Escenario A (por iteración)**

- El daemon **vuelve a arrancar** tras el `kill -9` y responde a `health` y a `status` en menos de 3 s.
- `speedyg.db` pasa `PRAGMA integrity_check` (resultado `ok`). Si existe `scheduler.json`, es JSON válido (nunca queda un archivo a medias en su ruta final).
- **Ningún ID aceptado** (respuesta `encolado correctamente` recibida antes del `kill -9`) falta en `status` tras reiniciar: lo que se confirmó al cliente no se pierde.
- Ningún ID aparece dos veces en `status`.
- Los trabajos no aceptados antes del `kill -9` pueden existir o no, pero si existen están completos: tienen comando, estado válido y fecha de recepción.
- El ID de un trabajo nuevo posterior al reinicio es **mayor** que cualquier ID presente: no se reutilizan IDs.

**Escenario C**

- **C1 y C2:** el estado recuperado coincide con la línea base (mismos IDs, estados, códigos de salida y comandos). Un archivo temporal parcial o un JSON dañado no impide recuperar desde la copia sana.
- **C3:** el estado se recupera desde la copia sana (JSON) y el daemon registra en `daemon.log` que la base no pudo leerse. Después de recuperar, el servicio **puede volver a persistir**: un trabajo nuevo sobrevive a otra interrupción. Un sistema que recupera una vez pero deja de guardar no es "recuperable".
- **C4:** el servicio no termina ni se bloquea, `health` responde, `status` no muestra trabajos que no existían y `daemon.log` registra el error de lectura. No se exige recuperar datos que ya no existen en ninguna copia.

### RNF-31 — Recuperación que distingue pendientes, terminados e interrumpidos

**Escenario B**

- D permanece `Succeeded` con exit code 0 y E permanece `Canceled`. La salida de `status` de ambos (comando, estados, recibido, iniciado, finalizado, código de salida) es **idéntica** antes y después del reinicio.
- A, que estaba `Running` cuando murió el servicio, se reporta como `Interrupted`. **Nunca** `Running` ni `Succeeded`: su proceso ya no estaba bajo control del servicio.
- B y C, que estaban `Queued`, conservan su ID y su orden, se relanzan y terminan en `Succeeded`; B termina antes de que C inicie (ranura única).
- A permanece `Interrupted` en todas las muestras posteriores: no regresa a `Running` ni a `Queued`.

**Escenario A**

- Tras esperar la recuperación, **ningún trabajo permanece** `Running` ni `Queued`. Todos están en un estado terminal: `Succeeded`, `Failed`, `Canceled` o `Interrupted`.
- Todo trabajo `Succeeded` tiene exit code 0. Ningún trabajo cambió de estado terminal a otro.

## 8. Criterios PASS/FAIL/BLOCKED

### PASS

Se cumplen **todos** los siguientes criterios en **las 10 iteraciones** del escenario A y en los escenarios B y C:

1. El daemon cargó la configuración solicitada en cada escenario.
2. Tras cada `kill -9` el daemon reinicia y responde `health` y `status` en menos de 3 s.
3. `speedyg.db` pasa `integrity_check` y `scheduler.json`, si existe, es JSON válido, tras cada interrupción.
4. Ningún ID aceptado antes del `kill -9` desaparece ni se duplica, y no se reutilizan IDs.
5. Tras la recuperación no queda ningún trabajo `Running` ni `Queued`, y todo `Succeeded` tiene exit code 0.
6. En el escenario B: D y E no cambian; A queda `Interrupted`; B y C terminan en `Succeeded` en orden.
7. En C1 y C2 el estado recuperado coincide con la línea base.
8. En C3 el estado se recupera, la recuperación se registra y un trabajo nuevo sobrevive a otra interrupción.
9. En C4 el servicio no se cae, responde `health`, no inventa trabajos y registra el error.
10. El daemon responde `health` al terminar.

### FAIL

Un solo incumplimiento en **cualquier** iteración o escenario es FAIL. En particular:

1. El daemon no vuelve a arrancar, se bloquea o termina tras una interrupción.
2. La base falla `integrity_check` o el JSON en su ruta final está truncado o es inválido.
3. Un trabajo aceptado antes del `kill -9` desaparece, aparece duplicado o aparece incompleto.
4. Se reutiliza un ID ya emitido.
5. Un trabajo que estaba `Running` al caer el servicio se reporta `Running`, `Succeeded` o `Failed` tras reiniciar en lugar de `Interrupted`.
6. Un trabajo terminado o cancelado cambia de estado, de código de salida o de datos tras el reinicio.
7. Un trabajo `Queued` se pierde, cambia de orden o nunca se relanza.
8. En C1 o C2 el estado recuperado difiere de la línea base.
9. En C3 no se recupera el estado, la recuperación no queda registrada, o después de recuperar el servicio deja de persistir (un trabajo nuevo se pierde tras otra interrupción).
10. En C4 el daemon termina, se bloquea, reporta trabajos inexistentes o no registra el error.

### BLOCKED

- El daemon no cargó la configuración esperada o no pudo iniciarse.
- No se pudo establecer el aislamiento de persistencia (`SPEEDYG_DB`, `SPEEDYG_JSON`).
- No hay `sqlite3` o `python3` disponibles: solo se marca como BLOCKED la comprobación de integridad correspondiente (criterio 3). Los demás criterios se siguen evaluando.

> Una interrupción justo durante una escritura es una carrera. Si el caso da PASS, el informe debe indicar el número de iteraciones (10) y declarar que no demuestra la ausencia de ventanas de corrupción más estrechas.
