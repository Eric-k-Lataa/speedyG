## 2. Objetivo

Verificar que el protocolo define compatibilidad de versión y que el daemon **rechaza de forma explícita** los mensajes con una versión incompatible o con un encabezado ausente o mal formado (RNF-32), sin crear trabajos y sin dejar de atender solicitudes posteriores.

Regla de compatibilidad que se verifica (ADR-06: versión en cada mensaje, sin *handshake*; implementada en `src/protocol.rs`):

- Cada mensaje lleva el encabezado `v=<major>.<minor>|<comando>` seguido de `\n`.
- Versión soportada por el daemon: `1.0`.
- Se **acepta** la misma versión mayor con versión menor igual o anterior.
- Se **rechaza** una versión mayor distinta, una versión menor superior a la soportada, y cualquier encabezado ausente o mal formado.
- El rechazo debe ser explícito: indica la versión recibida y las versiones soportadas.

> Los resultados esperados se derivan de RNF-32 y del ADR-06, no del comportamiento observado del código.

> **Nota sobre ADR-06.** El ADR habla de versión SemVer, pero el formato definido y aplicado es `major.minor` (sin parche). Este caso verifica `major.minor`. Un encabezado con tres componentes (`v=1.0.0`) no se prueba aquí.

## 3. Precondiciones

1. El proyecto debe compilar correctamente (`cargo build`). El script usa los binarios de `target/debug/`.
2. El script de verificación debe tener permisos de ejecución (`verif/scripts/TC-023.sh`).
3. `python3` disponible: el cliente `speedyg` siempre adjunta la versión actual, así que los mensajes con versión incorrecta se envían con `verif/scripts/lib/net_probe.py`. Si no está disponible, el caso queda **BLOCKED**.
4. Socket Unix y directorio de datos temporales aislados por corrida (`setup_run_env`), con persistencia explícita en `SPEEDYG_DB` o `SPEEDYG_JSON`. No depende de `/tmp/speedyg.sock`.
5. El daemon se inicia con parámetros explícitos:

```bash
speedyG --socket <socket-temporal> --data-dir <datos-temporales>
```

6. El daemon inicia sin trabajos previos (datos temporales vacíos); el script lo comprueba con `status` antes de empezar.

## 4. Datos de prueba

Cada mensaje se escribe en `$RUN_DIR/payloads/` y se envía completo, terminado en `\n`, por una conexión nueva.

| Id | Mensaje enviado | Tipo | Resultado esperado |
| --- | --- | --- | --- |
| M-01 | `v=1.0\|health` | Versión actual (soportada) | Aceptado |
| M-02 | `v=2.0\|health` | Versión mayor superior | Rechazado |
| M-03 | `v=0.9\|health` | Versión mayor anterior | Rechazado |
| M-04 | `v=1.1\|health` | Versión menor superior a la soportada | Rechazado |
| M-05 | `health` | Sin encabezado | Rechazado |
| M-06 | `1.0\|health` | Sin prefijo `v=` | Rechazado |
| M-07 | `v=abc\|health` | Versión no numérica | Rechazado |
| M-08 | `v=1\|health` | Sin versión menor | Rechazado |
| M-09 | `v=2.0\|sleep 5` | Versión incompatible con un comando que crearía un trabajo | Rechazado, sin trabajo creado |

| Dato | Valor |
| --- | --- |
| Envío posterior a los rechazos | `v=1.0\|echo recuperado` y `health` |
| Tiempo máximo de respuesta de un rechazo | 3 s |
| Tiempo máximo del caso | 30 s |

> Mientras el daemon soporte `1.0`, no existe una versión menor anterior dentro de la mayor `1`, así que M-01 es también el límite inferior aceptado. Si el daemon sube su versión menor, hay que añadir un mensaje con una menor anterior que sea aceptado.

## 5. Procedimiento

1. Ejecutar `cargo build`.
2. Ejecutar `./verif/scripts/TC-023.sh`.
3. El script arranca el daemon (sección 3) y comprueba con `status` que no hay trabajos.
4. Envía M-01 y registra la respuesta (línea base: la versión actual se acepta).
5. Envía M-02 a M-08 por conexiones independientes y registra, para cada una, la respuesta literal y el tiempo de respuesta.
6. Envía M-09 y consulta `status` para comprobar que no se creó ningún trabajo.
7. Comprueba con una conexión nueva (`health`) que el daemon sigue respondiendo después de los rechazos.
8. Envía `v=1.0|echo recuperado` y comprueba que es aceptado (el servicio se recupera tras los rechazos).
9. Consulta `status` y compara con el paso 3: solo existe el trabajo `echo recuperado`, y los rechazos no consumieron ID.
10. Revisa `daemon.log` y comprueba que no quedan procesos del daemon tras detenerlo.

## 6. Resultados esperados

### RNF-32 — El protocolo deberá definir compatibilidad de versión y rechazar mensajes incompatibles de forma explícita

- M-01 devuelve la respuesta normal de `health` (primera línea `status=active`).
- M-02 a M-08 **no** devuelven la respuesta de `health`; devuelven un mensaje que empieza con `Error de protocolo:`.
- Cada rechazo llega en menos de 3 s.
- El mensaje de rechazo de M-02, M-03 y M-04 incluye la **versión recibida** (`2.0`, `0.9` y `1.1`) y las **versiones soportadas** (`1.x` o `1.0`).
- El mensaje de rechazo de M-05 a M-08 indica la causa del encabezado inválido: ausente (M-05), sin prefijo `v=` (M-06) o sin formato `<major>.<minor>` (M-07 y M-08).
- El rechazo ocurre sin ejecutar el comando: ni M-09 ni los demás mensajes rechazados crean trabajos.

### Continuidad del servicio

- Tras los rechazos, `health` responde en una conexión nueva.
- `v=1.0|echo recuperado` es aceptado y recibe el primer ID del daemon (los rechazos no consumen ID).
- El daemon no termina ni queda bloqueado.

### Registro

- `daemon.log` contiene una entrada por cada rechazo de protocolo generada durante esta corrida.

## 8. Criterios PASS/FAIL/BLOCKED

### PASS

Se cumplen **todos** los siguientes criterios:

1. M-01 (versión actual) es aceptado y devuelve la respuesta de `health`.
2. M-02 a M-08 son rechazados con una respuesta que empieza con `Error de protocolo:`.
3. Los rechazos de M-02, M-03 y M-04 incluyen la versión recibida y las versiones soportadas.
4. Los rechazos de M-05 a M-08 indican la causa del encabezado inválido (ausente, sin prefijo `v=` o sin formato `<major>.<minor>`).
5. Cada rechazo llega en menos de 3 s.
6. M-09 no crea ningún trabajo: `status` no cambia.
7. Tras los rechazos, `health` responde y `echo recuperado` es aceptado con el primer ID.
8. `daemon.log` registra los rechazos de protocolo de esta corrida.
9. El daemon sigue activo durante todo el caso y no quedan procesos huérfanos al detenerlo.

### FAIL

1. Un mensaje con versión incompatible, encabezado ausente o mal formado es aceptado o ejecutado.
2. El rechazo no es explícito (respuesta vacía, cierre de conexión sin mensaje, o mensaje sin versión recibida y soportada).
3. Un mensaje rechazado crea un trabajo o consume un ID.
4. La versión actual (M-01) es rechazada.
5. El daemon termina, se bloquea o deja de responder tras un rechazo.
6. Un rechazo supera el tiempo máximo de respuesta.
7. Los rechazos no quedan registrados en `daemon.log`.

### BLOCKED

- `python3` no está disponible.
- El daemon no pudo iniciarse o el aislamiento de persistencia no pudo establecerse.
