# TC-003 — Estados y tiempos de un trabajo

## 1. Identificación

| Campo | Valor |
| ------- | ------- |
| **ID** | TC-003 |
| **Título** | Estados y tiempos de un trabajo |
| **Prioridad** | Alta |

| **Tipo** | Funcional / Integración |
| **Requisitos** | RF-06, RF-07 |
| **Estado** | Pendiente |

## 2. Objetivo

Verificar que el servicio representa el ciclo de vida de un trabajo con los estados exigidos (RF-06) y que registra los tiempos de recepción, inicio y terminación, además del código de salida (RF-07).

Con el límite de concurrencia en **1** se fuerza una ejecución en serie, de modo que un trabajo espere en `Queued` mientras otro está en `Running`. El caso observa:

1. `Queued → Running → Succeeded` (trabajos A y B).
2. `Queued → Running → Failed` con código de salida distinto de 0 (trabajo C).
3. `Queued → Canceled` (trabajo D, cancelado mientras está en cola).
4. Que ningún trabajo muestre una transición imposible: regresión de estado o cambio entre estados terminales.
5. Que se cumpla `received ≤ started ≤ finished` y que los tiempos sean coherentes con lo ocurrido realmente.

> Los resultados esperados se derivan de los requisitos (RF-06, RF-07) y de este contrato, no del comportamiento observado del código.

## 3. Precondiciones

1. El proyecto debe compilar correctamente (`cargo build`). El script usa `target/debug/`.
2. El script debe tener permisos de ejecución (`verif/scripts/TC-003.sh`).
3. Socket Unix y directorio de datos son **temporales y propios de la corrida** (`setup_run_env`).
4. Persistencia aislada mediante `SPEEDYG_DB` y `SPEEDYG_JSON` apuntando al directorio temporal.
5. El daemon se inicia con parámetros explícitos:

```bash
speedyG --socket <socket-temporal> --data-dir <datos-temporales> --max-current 1 --queue-cap 3
```

6. El script comprueba en `daemon.log` que `max_current=1` y `queue_cap=3`; si no, el caso queda **BLOCKED**.
7. La **parte B (tiempos)** requiere que `status <id>` exponga los tiempos (issue A2-07). Si no los expone, esa parte queda **BLOCKED**, no FAIL.

## 4. Datos de prueba

| Trabajo | Comando | Comportamiento esperado |
| --- | --- | --- |
| A | `sleep 3` | `Running` ≈ 3 s → `Succeeded`, exit code 0 |
| B | `sleep 2` | Espera en `Queued` a que termine A → `Running` ≈ 2 s → `Succeeded`, exit code 0 |
| C | `timeout 1 sleep 5` | `Queued` → `Running` ≈ 1 s → `Failed`, exit code 124 |
| D | `sleep 1` | Se cancela en `Queued` → `Canceled`, nunca se ejecuta |

Los trabajos se envían en el orden A, B, C, D, de forma secuencial.

Justificación:

- Con límite 1 y `sleep 3`, B y C permanecen en `Queued` el tiempo suficiente para observarlos.
- `timeout 1 sleep 5` produce un fallo determinista (código 124) sin depender de comandos inexistentes.
- D se cancela antes de que le toque ejecutarse, lo que permite comprobar `Queued → Canceled`.

### 4.1 Parámetros del muestreo

| Parámetro | Valor |
| --- | --- |
| Intervalo entre muestras | 0,1 s |
| Inicio del muestreo | Inmediatamente antes del primer envío |
| Fin del muestreo | Cuando A, B y C están en estado terminal o se agotan 30 s |

Un trabajo de 1 s (C) produce unas 8 a 10 muestras en `Running`, suficientes para observar el estado.

## 5. Procedimiento

1. Ejecutar `cargo build`.
2. Ejecutar `./verif/scripts/TC-003.sh`.
3. El script crea el entorno, arranca el daemon (sección 3) y valida la configuración efectiva.
4. Inicia el muestreo en segundo plano de `status` con marca de tiempo.
5. Envía A, B, C y D y registra los IDs.
6. Tras 0,5 s consulta `status <id>` de A y de B y guarda ambas respuestas (instantáneas en `Running` y en `Queued`).
7. Cancela D mientras está en cola.
8. Espera a que A, B y C estén en estado terminal (máximo 30 s) y detiene el muestreo.
9. Consulta el estado final de A, B, C y D.
10. **Parte A:** reconstruye la secuencia de estados de cada trabajo a partir de las muestras y evalúa los criterios de la sección 6.
11. **Parte B:** extrae `received`, `started` y `finished` de cada trabajo y evalúa los criterios de tiempos.
12. Comprueba que no quedan procesos hijos del daemon y detiene el daemon.

## 6. Resultados esperados

### RF-06 — Estados de un trabajo (parte A)

- A: secuencia `Running → Succeeded`, precedida opcionalmente de `Queued`.
- B: `Queued → Running → Succeeded`.
- C: `Queued → Running → Failed`.
- D: `Queued → Canceled`.
- En la instantánea tomada a los 0,5 s, A está en `Running` y B en `Queued`.
- Ningún trabajo regresa a un estado anterior (`Running → Queued`) ni cambia entre estados terminales (`Succeeded → Failed`, `Canceled → Running`, etc.).
- En ninguna muestra hay más de 1 trabajo en `Running`.

### RF-07 — Código de salida (parte A)

- A y B terminan con `exit code: 0`.
- C termina con `exit code: 124`.
- D responde `cancelado correctamente` y no tiene código de salida.

### RF-07 — Tiempos (parte B)

El contrato que exige este caso para `status <id>`:

| Tiempo | Etiqueta aceptada (insensible a mayúsculas) | Formato aceptado |
| --- | --- | --- |
| Recepción | `received`, `recibido`, `recepción` | ISO-8601 o epoch (segundos o milisegundos) |
| Inicio | `started`, `iniciado`, `inicio` | ídem |
| Terminación | `finished`, `terminado`, `terminación`, `finalizado` | ídem |

Para cada trabajo A, B y C:

- Se exponen los tres tiempos.
- `received ≤ started ≤ finished`.
- Los tres caen dentro de la ventana real de la prueba (±2 s). Esto evita aceptar valores inventados o con otra zona horaria.

Además:

- La duración de A (`finished − started`) es al menos 2,5 s (`sleep 3`).
- B esperó en cola al menos 2,0 s (`started − received`).
- B inició después de terminar A, y C después de terminar B (ranura única).
- Un trabajo en `Queued` tiene `received` pero no `started` ni `finished`.
- Un trabajo en `Running` tiene `received` y `started` pero no `finished`.

## 8. Criterios PASS/FAIL/BLOCKED

### PASS

Se cumplen **todos** los criterios de las partes A y B:

1. El daemon cargó `max_current=1` y `queue_cap=3`.
2. Los 4 envíos son aceptados con IDs distintos.
3. Las secuencias de A, B, C y D coinciden con la sección 6.
4. No hay regresiones ni cambios entre estados terminales.
5. Nunca hay más de 1 trabajo en `Running`.
6. Los códigos de salida son 0, 0 y 124 para A, B y C.
7. Los tiempos de A, B y C cumplen `received ≤ started ≤ finished` y la coherencia de la sección 6.
8. Al terminar no quedan procesos hijos ni zombis del daemon.

### FAIL

1. Una secuencia de estados difiere de la esperada, hay una regresión o un cambio entre estados terminales.
2. Hay más de 1 trabajo en `Running`.
3. Un código de salida no coincide con el esperado.
4. Los tiempos se exponen pero no cumplen `received ≤ started ≤ finished`, caen fuera de la ventana o son incoherentes con la duración real.
5. Un trabajo no llega a estado terminal en 30 s.
6. Quedan procesos hijos o zombis del daemon.

### BLOCKED

- El daemon no cargó la configuración esperada o no pudo iniciarse.
- **La parte B no pudo evaluarse porque `status <id>` no expone ningún tiempo** (falta A2-07). En este caso la parte A se evalúa igualmente y el resultado global es `BLOCKED` si la parte A no tiene FAIL. El script termina con código 3.

RF-06 puede pasar a PASS con la parte A. RF-07 solo pasa a PASS cuando la parte B se evalúa y cumple.
