# TC-021 — Escalamiento de cancelación

## 1. Identificación

| Campo | Valor |
| ------- | ------- |
| **ID** | TC-021 |
| **Título** | Escalamiento de cancelación ante trabajos que ignoran SIGTERM |
| **Prioridad** | Crítica |
| **Método** | Prueba |
| **Tipo** | Robustez / Integración / Señalización / Gestión de Procesos |
| **Requisitos** | RF-30, RNF-30 |
| **Estado** | Pendiente |

## 2. Objetivo

Verificar la política de escalamiento de señales durante la cancelación de un trabajo que no responde a la terminación estándar (`SIGTERM`) y genera procesos subordinados (nietos), conforme a **RF-30** y **RNF-30**:

1. **RF-30 (Política de escalamiento documentada y verificable):** Si un trabajo no termina tras la solicitud normal de cancelación (por ejemplo, porque ignora `SIGTERM` mediante `trap '' TERM`), el daemon debe aplicar la política de escalamiento: esperar el periodo de gracia configurado (`grace_ms`) y enviar forzosamente `SIGKILL` a todo el grupo de procesos (`process_group`).
2. **RNF-30 (Sin procesos huérfanos ni subprocesos residuales):** El escalamiento con `SIGKILL` al grupo de procesos debe terminar tanto al proceso hijo directo como a cualquier proceso nieto derivado, dejando el sistema libre de procesos huérfanos y zombis, y registrando el trabajo en el estado terminal `Canceled`.

> Los resultados esperados se derivan de **RF-30** y **RNF-30**, garantizando que el mecanismo de cancelación forzada recupera los recursos y ranuras de concurrencia independientemente del comportamiento interno del comando ejecutado.

## 3. Precondiciones

1. El proyecto debe compilar correctamente (`cargo build`). El script usa el binario generado en `target/debug/speedyG`.
2. El script de verificación debe tener permisos de ejecución (`verif/scripts/TC-021.sh`).
3. Socket Unix y directorio de datos temporales aislados por corrida (`setup_run_env`), con persistencia explícita en `SPEEDYG_DB` o `SPEEDYG_JSON`.
4. El daemon se inicia con un tiempo de gracia explícito y reducido (`--grace-ms 1000`) para verificar el escalamiento dentro de una ventana temporal predecible:

```bash
speedyG --socket <socket-temporal> --data-dir <datos-temporales> --max-current 2 --queue-cap 5 --grace-ms 1000
```

5. El script verifica en `daemon.log` que la configuración efectiva coincide con la solicitada (`max_current=2`, `grace_ms=1000`); en caso contrario, el caso queda **BLOCKED**.
6. Se dispone de utilidades del sistema (`pgrep`, `kill`, `ps`) para rastrear procesos e inspeccionar el grupo de procesos en el SO.

## 4. Datos de prueba

| Identificador | Comando | Estado inicial | Papel en la prueba | Requisito evaluado |
| --- | --- | --- | --- | --- |
| **J1** | `sh -c "trap '' TERM; sleep 2002 & wait"` | `Running` | **Trabajo reacio a SIGTERM:** Ignora SIGTERM y genera un proceso nieto (`sleep 2002`) en segundo plano | RF-30, RNF-30 |
| **J2** | `echo siguiente-tras-escalamiento` | `Queued` | **Trabajo en cola:** Debe avanzar a `Running → Succeeded` al liberarse la ranura | RF-30 |

### 4.1 Parámetros temporales

| Parámetro | Valor |
| --- | --- |
| Concurrencia máxima (`max_current`) | `1` |
| Tiempo de gracia antes de escalar (`grace_ms`) | `1000` ms (1 s) |
| Tiempo de estabilización de J1 en `Running` | 2 s |
| Tiempo de escalamiento esperado (SIGTERM → SIGKILL) | ~1 s (`grace_ms`) |
| Tiempo máximo para que J1 alcance `Canceled` | ≤ 5 s |
| Tiempo máximo para que J2 complete su ejecución | ≤ 5 s |
| Timeout total del caso | 45 s |

## 5. Procedimiento

1. Compilar el proyecto con `cargo build`.
2. Ejecutar `./verif/scripts/TC-021.sh`.
3. Iniciar el daemon con `--max-current 1 --queue-cap 5 --grace-ms 1000`.
4. Registrar el PID del daemon y validar la configuración cargada (`daemon-pid.txt`).
5. **Fase 1 — Lanzamiento del trabajo reacio y trabajo en cola:**
   - Enviar J1 con el comando que atrapa e ignora SIGTERM y lanza el nieto `sleep 2002`.
   - Enviar J2 (`echo siguiente-tras-escalamiento`).
   - Esperar 2 s a que J1 pase a `Running` y J2 a `Queued`.
   - Registrar el estado inicial en `status-pre-cancel.txt`.
6. **Fase 2 — Identificación del árbol de procesos (hijo y nieto en el SO):**
   - Localizar el PID del subproceso hijo directo de J1 (`sh`).
   - Localizar el PID del subproceso nieto (`sleep 2002`).
   - Registrar los PIDs en `pids-pre-cancel.txt`.
7. **Fase 3 — Solicitud de cancelación y escalamiento (RF-30):**
   - Registrar la marca de tiempo de inicio de la cancelación.
   - Enviar `client cancel <ID_J1>` y guardar la respuesta en `cancel-response.txt`.
   - Verificar que el proceso no muere inmediatamente con SIGTERM (dado el trap).
   - Comprobar que transcurrido el tiempo de gracia (`~1000 ms`), el daemon escala a `SIGKILL` sobre el grupo de procesos.
8. **Fase 4 — Verificación de estado terminal y avance de cola (RF-30):**
   - Consultar `status <ID_J1>` y verificar que transicionó a `Canceled` (`status-j1-post-cancel.txt`).
   - Esperar a que J2 sea despachado y culmine exitosamente en `Succeeded` con código `0` (`status-j2-post-cancel.txt`).
9. **Fase 5 — Verificación de eliminación completa del árbol de procesos (RNF-30):**
   - Comprobar en el SO que ni el proceso hijo ni el proceso nieto (`sleep 2002`) continúan en ejecución (`orphans-check.txt`).
   - Verificar con `ps` que no existen procesos zombis (`STAT Z`) bajo el daemon (`zombies-check.txt`).
10. **Fase 6 — Verificación de salud y cierre:**
    - Consultar `health` del daemon y validar respuesta `OK` (`health-check.txt`).
    - Detener el daemon y concluir el caso.

## 6. Resultados esperados

### RF-30 — Escalamiento de cancelación documentado y verificable

- Al solicitar `cancel <ID_J1>`, el daemon envía `SIGTERM`. Al ignorarse la señal, tras agotar el tiempo de gracia (`grace_ms=1000`), el daemon envía `SIGKILL` al grupo de procesos.
- El trabajo J1 termina y pasa al estado terminal `Canceled`.
- La ranura de ejecución se libera, permitiendo que J2 avance de `Queued` a `Running` y finalice en `Succeeded` con exit code `0`.

### RNF-30 — Eliminación total de procesos huérfanos y nietos

- El proceso hijo directo (`sh`) y el proceso nieto (`sleep 2002`) son completamente terminados en el sistema operativo.
- `pgrep -f "sleep 2002"` no devuelve ningún PID tras el escalamiento.
- El subproceso es cosechado por el runtime del daemon, sin dejar procesos zombis (`STAT Z`).

## 8. Criterios PASS/FAIL/BLOCKED

### PASS

Se cumplen **todos** los siguientes criterios:

1. El daemon inicia y carga la configuración requerida (`max_current=1`, `grace_ms=1000`).
2. J1 entra en `Running` e inicia tanto su proceso principal como su proceso nieto (`sleep 2002`).
3. Al cancelar J1, el daemon escala a `SIGKILL` tras el tiempo de gracia (`grace_ms`).
4. J1 alcanza el estado terminal `Canceled` (RF-30).
5. Ni el proceso hijo ni el proceso nieto (`sleep 2002`) quedan vivos en el sistema operativo (RNF-30).
6. J2 avanza de `Queued` a `Running` y culmina en `Succeeded` con código `0` (RF-30).
7. No se generan procesos zombis (`STAT Z`) bajo el PID del daemon (RNF-30).
8. El daemon responde satisfactoriamente a `health`.

### FAIL

1. El trabajo J1 permanece en `Running` indefinidamente porque el daemon no escala a `SIGKILL` (violación de RF-30).
2. El proceso nieto (`sleep 2002`) sobrevive en el sistema operativo como proceso huérfano (violación de RNF-30).
3. J1 no transiciona al estado `Canceled` tras la cancelación (violación de RF-30).
4. J2 no avanza tras liberarse la ranura de concurrencia (violación de RF-30).
5. Quedan procesos zombis bajo el daemon (violación de RNF-30).
6. El daemon termina o se reinicia de forma anómala durante el escalamiento.

### BLOCKED

- El daemon no pudo iniciarse o no cargó la configuración esperada (`grace_ms=1000`).
- Las utilidades del sistema (`kill`, `pgrep`, `ps`) no están disponibles en el entorno.
