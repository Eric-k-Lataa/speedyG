# TC-005 — Cancelar un trabajo en cola y en ejecución

## 1. Identificación

| Campo | Valor |
| ------- | ------- |

| **Título** | Cancelar un trabajo en cola y en ejecución |
| **Prioridad** | Crítica |

| **Requisitos** | RF-10 (principal); RNF-21 y RNF-30 (mensaje de error y procesos residuales, evaluados en este caso) |
| **Estado** | Pendiente |

## 2. Objetivo

Verificar que el usuario puede cancelar un trabajo que está en cola y uno que está en ejecución, y que el sistema refleja el resultado (RF-10):

1. Cancelar un trabajo `Queued` lo lleva a `Canceled` sin que llegue a ejecutarse.
2. Cancelar un trabajo `Running` lo lleva a `Canceled` **y el proceso del trabajo deja de existir** (el sistema operativo lo demuestra, no solo el estado reportado).
3. Al liberarse la capacidad, el siguiente trabajo en cola avanza.
4. Cancelar un trabajo ya terminado, ya cancelado o inexistente devuelve un error claro y no cambia ningún estado.

> Los resultados esperados se derivan de RF-10 y del ADR-04 (decisiones 3 a 5), no del comportamiento observado del código. La política de escalamiento SIGTERM→SIGKILL se verifica en TC-021.

## 3. Precondiciones

1. El proyecto debe compilar (`cargo build`). El script usa `target/debug/`.
2. El script debe tener permisos de ejecución (`verif/scripts/TC-005.sh`).
3. Socket Unix y directorio de datos temporales y propios de la corrida (`setup_run_env`); persistencia aislada con `SPEEDYG_DB` y `SPEEDYG_JSON`.
4. El daemon se inicia con parámetros explícitos:

```bash
speedyG --socket <socket-temporal> --data-dir <datos-temporales> --max-current 1 --queue-cap 3
```

5. El script comprueba en `daemon.log` que `max_current=1` y `queue_cap=3`; si no, el caso queda **BLOCKED**.
6. **Dependencias de implementación:** la cancelación de un trabajo `Running` que termina el proceso es el issue A2-08, y la serialización de estados es A2-11. Si la cancelación existe pero el proceso sigue vivo, el resultado es **FAIL** (defecto real), no BLOCKED.

## 4. Datos de prueba

Cada trabajo usa un argumento único para poder localizar su proceso en el sistema operativo aunque cambie su proceso padre:

| Trabajo | Comando | Papel |
| --- | --- | --- |
| A | `sleep 1001` | Pasa a `Running` (única ranura) y se cancela en ejecución |
| B | `sleep 1002` | Queda en `Queued` y se cancela en cola |
| C | `echo siguiente` | Queda en `Queued` y debe avanzar al liberarse la ranura de A |

Los trabajos se envían en el orden A, B, C.

### 4.1 Parámetros

| Parámetro | Valor |
| --- | --- |
| Tiempo máximo para que el proceso de A desaparezca tras cancelar | 5 s |
| Tiempo de observación posterior a la cancelación (sin regresión de estado) | 3 s |
| Intervalo de muestreo de estados | 0,1 s |
| Tiempo máximo del caso | 60 s |

### 4.2 Cómo se localiza el proceso de un trabajo

Antes de cancelar A, el script registra:

- Los hijos directos del daemon: `pgrep -P <PID del daemon>`.
- Todos los procesos cuyo comando contiene el marcador: `pgrep -f "sleep 1001"`.

Después de cancelar, comprueba que **ninguno de esos PID existe** (`/proc/<pid>`) y que `pgrep -f "sleep 1001"` no devuelve resultados. Así se detectan también los procesos nietos reasignados a `init` (`ppid=1`), que un conteo de hijos directos no vería.

## 5. Procedimiento

1. Ejecutar `cargo build` y `./verif/scripts/TC-005.sh`.
2. El script crea el entorno, arranca el daemon y valida la configuración.
3. Inicia el muestreo en segundo plano de `status` (0,1 s).
4. Envía A, B y C y comprueba que A está `Running`, y B y C `Queued`.
5. **Cancelación en cola:** cancela B, registra la respuesta y consulta su estado.
6. **Cancelación en ejecución:** registra los PID del trabajo A, lo cancela, registra la respuesta y espera hasta 5 s a que sus procesos desaparezcan.
7. Observa 3 s más para verificar que A permanece `Canceled`.
8. Espera a que C pase a `Running` y a `Succeeded`.
9. **Cancelación inválida:** cancela C (terminado), cancela A de nuevo (ya cancelado), cancela un ID inexistente y envía `cancel` sin ID y con un ID no numérico.
10. Consulta el estado final de A, B y C, comprueba que el daemon responde `health` y que no quedan procesos hijos ni zombis.

## 6. Resultados esperados

### RF-10 — Cancelar un trabajo en cola

- La respuesta de `cancel <B>` indica que el trabajo B fue cancelado e incluye su ID.
- `status <B>` muestra `Canceled`.
- B **nunca** aparece en `Running` en las muestras y su proceso (`sleep 1002`) nunca existe en el sistema.
- A sigue en `Running` y C sigue en `Queued` inmediatamente después.

### RF-10 — Cancelar un trabajo en ejecución

- La respuesta de `cancel <A>` indica que el trabajo A fue cancelado e incluye su ID.
- Dentro de 5 s, `status <A>` muestra `Canceled`.
- Dentro de 5 s, ninguno de los PID registrados de A existe y `pgrep -f "sleep 1001"` no devuelve resultados.
- Durante los 3 s posteriores A permanece `Canceled` (no vuelve a `Running` ni pasa a `Succeeded` o `Failed`).
- El daemon no tiene hijos zombis.

### RF-10 — El sistema refleja el resultado

- Al liberarse la ranura de A, C pasa `Queued → Running → Succeeded` con `exit code: 0`.
- La secuencia de estados observada para B es `Queued → Canceled` y para A `Running → Canceled`, sin regresiones.

### RF-10 / RNF-21 — Cancelación inválida

| Solicitud | Respuesta esperada | Efecto |
| --- | --- | --- |
| `cancel <C>` (terminado) | Error que incluye el ID de C y el motivo (ya terminó / estado `Succeeded`); no afirma haber cancelado | C sigue `Succeeded`, exit code 0 |
| `cancel <A>` (ya cancelado) | Respuesta que incluye el ID y que indica que ya estaba cancelado; no afirma una nueva cancelación | A sigue `Canceled` |
| `cancel <ID inexistente>` | Error explícito de que el trabajo no existe, con el ID | Ninguno |
| `cancel` sin ID | Mensaje de uso | Ninguno |
| `cancel abc` | Mensaje de que el ID debe ser numérico | Ninguno |

Una respuesta genérica sin causa (por ejemplo, solo "no se pudo cancelar") **no** cumple el criterio.

## 8. Criterios PASS/FAIL/BLOCKED

### PASS

Se cumplen **todos** los criterios:

1. El daemon cargó `max_current=1` y `queue_cap=3`.
2. A está `Running`, y B y C `Queued`, antes de cancelar.
3. B termina `Canceled`, nunca aparece `Running` y su proceso nunca existe.
4. A termina `Canceled` y sus procesos desaparecen en 5 s.
5. Ningún trabajo cancelado cambia de estado en la observación posterior.
6. C avanza a `Running` y termina `Succeeded` con exit code 0.
7. Las cancelaciones inválidas cumplen la tabla de la sección 6 y no modifican estados.
8. El daemon responde `health` y no quedan procesos hijos, zombis ni procesos con los marcadores `sleep 1001` o `sleep 1002`.

### FAIL

1. El estado reportado es `Canceled` pero el proceso de A sigue vivo.
2. B llega a ejecutarse.
3. Un trabajo cancelado regresa a `Running` o cambia a `Succeeded` o `Failed`.
4. C no avanza tras liberarse la ranura.
5. Una cancelación inválida devuelve éxito, no incluye la causa o cambia un estado.
6. Quedan procesos huérfanos o zombis.

### BLOCKED

El daemon no cargó la configuración esperada o no pudo iniciarse.
